# IRNetFree روی OpenWrt — روتر، تونلِ همهٔ دستگاه‌ها

از **v1.13.0**. همان برنامه (همان UI، همان منطق: ساب، زنجیره، پول، روتینگ، PattN، fastest) روی روتر
اجرا می‌شود و **هر دستگاهی که به روتر وصل است بدون هیچ تنظیمی از تونل می‌رود** — تلویزیون، کنسول، گوشیِ مهمان.
دستگاه‌هایی که بخواهی، با MAC، مستقیم می‌روند.

## روتر مناسب

- OpenWrt **24.10** (`node` 20 در فید) یا **23.05** (`node` 18) — هر دو در CI روی QEMU تست می‌شوند. 22.03 و
  قدیمی‌تر نه؛ 25/SNAPSHOT هم نه (apk به‌جای opkg).
- حداقل **256MB RAM** و **128MB فضا** (خودِ Node ~۳۶ مگ نصب می‌شود، هسته‌ها ۲۰–۴۰ مگ هرکدام؛ در اجرا ~۱۰۰–۱۵۰ مگ RAM).
- اولین هدف: **Google Wifi نسل اول (AC-1304)** — ipq40xx، ARMv7 چهارهسته، 512MB/4GB. صفحهٔ دستگاه در ویکی OpenWrt:
  `google_wifi` زیر `ipq40xx/chromium`؛ اول `squashfs-factory.bin` بعد برای به‌روزرسانی `sysupgrade.bin`.
- روترهای ۳۲–۶۴ مگی (MIPS ارزان) هدف نیستند: Node در آن‌ها جا نمی‌شود.

## نصب — یک خط روی روتر

```sh
sh -c "$(wget -q -O - https://raw.githubusercontent.com/sadrazkh/Irnetfree_xray-client/main/openwrt/install.sh)"
```

وابستگی‌ها را نصب می‌کند، تازه‌ترین `irnetfree_<v>_all.ipk` را از ریلیز می‌گیرد، سرویس را بالا می‌آورد و لینک با توکن
را چاپ می‌کند. دوباره اجرا کردنش = به‌روزرسانی. اگر روتر به گیت‌هاب نمی‌رسد:

```sh
# روی کامپیوتر: ipk را از صفحهٔ ریلیز بگیر، بعد
scp irnetfree_<v>_all.ipk root@192.168.1.1:/tmp/
# روی روتر
wget -q -O /tmp/install.sh https://raw.githubusercontent.com/sadrazkh/Irnetfree_xray-client/main/openwrt/install.sh
sh /tmp/install.sh /tmp/irnetfree_<v>_all.ipk
```

دستی، بدون نصب‌کننده:

```sh
opkg update
opkg install node kmod-tun nftables ip-full unzip ca-bundle
opkg install /tmp/irnetfree_<v>_all.ipk
```

نصب، سرویس را فعال و اجرا می‌کند و یک zone فایروال به نام `irnetfree` برای دستگاه تونل می‌سازد (یک‌بار). هر zoneی
که به `wan` فوروارد می‌کند (lan، و مثلاً Wi-Fi مهمان یا یک VLAN) یک forwarding به `irnetfree` هم می‌گیرد — در نصب،
در هر به‌روزرسانی و در هر بار شروع سرویس (برای zoneی که بعداً ساخته شده)؛ وگرنه آن شبکه وقتی گیت‌وی بالاست اینترنت ندارد.
هر push در گیت‌هاب هم یک بستهٔ آزمایشی می‌سازد: Actions → Tests → artifact `IRNetFree-OpenWrt-dev`.

**بعد از به‌روزرسانی**، اگر LuCI صفحه‌های قدیمی یا بدون تب نشان داد: یک بار از LuCI خارج شو (Logout)، دوباره وارد شو و
صفحه را با Ctrl+F5 تازه کن. تا v1.16.0 همهٔ فایل‌های بسته تاریخ ۱۹۷۰ داشتند و مرورگر نسخهٔ قدیمیِ صفحه‌ها را سال‌ها
«تازه» حساب می‌کرد؛ از v1.16.1 فایل‌ها تاریخ کامیتِ همان نسخه را دارند.

## OpenWrt روی Google Wifi (AC-1304)

خلاصهٔ [صفحهٔ دستگاه در ویکی OpenWrt](https://openwrt.org/toh/google/wifi) — قبل از شروع خودِ صفحه را بخوان.
لوازم: هاب USB-C با Power Delivery (هر هابی کار نمی‌کند؛ ویکی مدل‌های تست‌شده را دارد)، فلش **USB 2.0**، پیچ‌گوشتی
PH0، و Chrome برای [OnHub Recovery Utility](https://chromewebstore.google.com/detail/onhub-recovery-utility/fmgkgdalfapcmjnanilfcpkhkhedmpdm).

1. **استوکِ تازه**: اگر دستگاه قبلاً دست‌کاری شده، اول با Recovery Mode گوگل (همان Utility، فلش ریکاوری: Reset را
   نگه دار، برق، ~۱۶ ثانیه، رها، فلش ریکاوری را بزن، ۵–۶ دقیقه) به کارخانه برگردان. مدل **GJ2CQ** (بدون USB-C)
   به لحیم‌کاری پورت USB روی TP1004–TP1007 نیاز دارد.
2. `openwrt-24.10.x-ipq40xx-chromium-google_wifi-squashfs-factory.bin` را با **OnHub Recovery Utility** (local
   image) روی فلش بنویس. `dd` روی خیلی از فلش‌ها بوت نمی‌شود؛ اگر `dd` می‌زنی، اول فلش را صفر کن.
3. قاب را باز کن (یک پیچ PH0) و **SW7** را پیدا کن. فلش و برق را به هاب وصل کن؛ هاب را هنوز به دستگاه نه.
4. **Reset** را نگه دار و هاب را وصل کن. سفید ثابت، آبی چشمک… ~۱۶ ثانیه بعد نارنجی چشمک → Reset را رها کن. ~۳
   ثانیه بعد نارنجی/کهربایی می‌تپد → **SW7** را بزن. یکی‌دو بار بنفش چشمک می‌زند و ریستارت می‌شود.
5. وقتی دوباره بنفش چشمک زد، **SW7**: LED خاموش می‌شود و از فلش بوت می‌کند (آبی تند → آهسته → ثابت). ~۳۰ ثانیه
   بعد، کابل LAN و `ping 192.168.1.1`. اگر برنگشت: ریکاوری گوگل و از اول؛ اگر بنفش نرفت، فلش دیده نشده (USB 2.0).
6. فریم‌ور را روی eMMC بنویس — دقیقاً دستورهای ویکی:
   ```sh
   ssh-keygen -f ~/.ssh/known_hosts -R 192.168.1.1
   scp -O openwrt-24.10.x-ipq40xx-chromium-google_wifi-squashfs-factory.bin root@192.168.1.1:/tmp/
   ssh root@192.168.1.1 "dd if=/dev/zero bs=512 seek=7634911 of=/dev/mmcblk0 count=33 && dd if=/tmp/openwrt-24.10.x-ipq40xx-chromium-google_wifi-squashfs-factory.bin of=/dev/mmcblk0"
   ```
7. فلش را دربیاور و ریبوت. آبی، مدتی بنفش (فرصت بوت از USB)، بعد OpenWrt از حافظهٔ داخلی. حالا خط نصب بالا.

## باز کردن UI

- **LuCI → Services → IRNetFree → Open IRNetFree** — لینک با توکن را می‌دهد.
- یا دستی: `cat /etc/irnetfree/token` و بعد `http://192.168.1.1:6969/?token=<توکن>`.
- خروجی نصب‌کننده هم همین لینک را چاپ می‌کند.

توکن بدون LuCI هم لازم است: سرویس روی `0.0.0.0` گوش می‌دهد و بدون توکن هیچ درخواستی را جواب نمی‌دهد. توکن فقط در
همان فایل است — نه در خط فرمان سرویس (`ps`) و نه در لاگ سیستم (`logread`)؛ سرویس با `--token-file` از فایل می‌خواندش.

## هسته‌ها

**اول: تنظیمات → فایل‌های موردنیاز.** همان دانلودر دسکتاپ است و برای ARMv7 فایل درست را می‌گیرد
(`Xray-linux-arm32-v7a`، `sing-box-…-linux-armv7`)، `geoip.dat` و `geosite.dat` را هم کنار xray می‌گذارد، و در
`/etc/irnetfree/bin` نصب می‌کند — که بر هستهٔ فید در `/usr/bin` مقدم است (برنامه `/usr/bin` را آخر از همه می‌گردد).

چرا نه فید: DNS شبکه — جوابِ REFUSED هستهٔ خودمان به پرسش‌های HTTPS/SVCB (نوع ۶۵) که گوشی‌ها و مرورگرها برای هر
نام تازه می‌فرستند، و `expectedIPs` برای resolver داخلی — روی **xray 26.3.27 و بالاتر** آزموده شده. `xray-core` فید
از آن قدیمی‌تر است (هنگام نوشتن: فید 23.05 نسخهٔ 24.12.31، فید 24.10 نسخهٔ 25.1.30): آن قاعده را نمی‌شناسد و آن
پرسش‌ها به‌جای REFUSED بی‌جواب می‌مانند. فید `geoip.dat`/`geosite.dat` هم ندارد، پس «دور زدن ایران» بی‌صدا مثل «همه
از تونل» کار می‌کند. نسخهٔ هسته‌ها: `/etc/irnetfree/bin/xray version | head -1` و `/usr/bin/xray version | head -1`.

فقط اگر «فایل‌های موردنیاز» از روتر به گیت‌هاب نمی‌رسد:

- **جایگزین:** `opkg install xray-core sing-box` — هسته‌های رسمی فید. `sing-box` فید برای تونل کافی است (CI گیت‌وی را
  با sing-box فید 23.05 و 24.10 آزمایش می‌کند)؛ `xray-core` فید را هر وقت دسترسی بود با دانلود عوض کن.
- یا فایل را روی کامپیوتر بگیر و `scp` کن به `/etc/irnetfree/bin/` (نام فایل‌ها: `xray`، `xray-pattn`، `sing-box`؛
  `chmod +x`؛ و `geoip.dat`، `geosite.dat` از zip خودِ xray). **PattN فقط از گیت‌هاب** می‌آید (در فید نیست).

## استفاده

**«گیت‌وی» یعنی چه؟** گیت‌وی = **روتر به‌عنوان تونل کل شبکه.** روتر «گیت‌وی» (دروازهٔ) شبکه است: هر دستگاهی که با
وای‌فای یا کابل به این روتر وصل شود، بدون هیچ تنظیمی روی خودِ دستگاه از تونل VPN می‌رود. این یک وضعیت است، نه گزینه —
روی روتر همیشه همین است و کلیدی برای انتخابش نیست: VPN وصل = همهٔ دستگاه‌ها از تونل، VPN قطع = همه مستقیم (کیل‌سوییچ،
پایین‌تر، فقط وقتی می‌بندد که VPN باید وصل باشد و تونل پایین است). در UI وب همین وضعیت در پنل «اینسپکتور» (حالت پیشرفته،
پنجرهٔ پهن) ردیف «تونل کل شبکه» است — تا v1.16.0 با نام «گیت‌وی: کل شبکه از تونل» — و در LuCI → Overview هم ردیف «تونل
کل شبکه». برای این‌که دستگاهی مستقیم برود: تنظیمات → دستگاه‌های شبکه (قدم ۳). هر جای این راهنما یا لاگ که «گیت‌وی»
(Gateway) آمده، همین است.

1. ساب یا لینک را اضافه کن (مثل دسکتاپ). حالت TUN پیش‌فرض روشن است — روی روتر یعنی «کل شبکه».
2. **وصل شو.** از این لحظه هر دستگاه پشت روتر از تونل می‌رود. DNS همهٔ دستگاه‌ها هم از تونل جواب می‌گیرد
   (dnsmasq روتر دست نمی‌خورد؛ بستهٔ پورت ۵۳ به تونل می‌رود و هستهٔ خود برنامه جواب می‌دهد). به همین دلیل
   «مدیریت DNS توسط برنامه» روی روتر **همیشه روشن** است و کلیدش در تنظیمات نشان داده نمی‌شود.
3. **تنظیمات → اجازه به شبکه محلی → دستگاه‌های شبکه**: فهرست دستگاه‌ها (از DHCP و جدول همسایه‌ها).
   تیک «مستقیم» یعنی آن دستگاه از تونل نمی‌رود؛ بی‌قطعی اعمال می‌شود.
4. **روتر همان‌طور می‌ماند که خودت گذاشتی.** اگر وصل بود، بعد از ریبوت، قطعی برق یا ری‌استارت سرویس خودش به **همان
   اتصال** برمی‌گردد (سرور، زنجیره یا روتینگ ویژه) — حتی اگر چند بار پشت‌سرهم برق برود قبل از این‌که دوباره وصل شود؛
   و تا وصل نشده دست برنمی‌دارد: پنج دقیقهٔ اول هر ۱۵ ثانیه، بعد هر دقیقه (WAN، مودم و ساعت روتر بعد از بوت دیر بالا
   می‌آیند) و در این مدت UI «منتظر اینترنت… (تلاش n)» نشان می‌دهد، نه خطا. اگر **خودت قطع کرده بودی**، بعد از ریبوت هم قطع
   می‌ماند. فقط قطع کردنِ دستی این «وصل بمان» را پاک می‌کند — نه خاموش شدن، نه قطعی برق، نه تلاشِ ناموفق. وصل یا قطع
   کردن دستی تلاش‌های در جریان را هم تمام می‌کند. این سوییچ روی روتر «**با روشن شدن روتر وصل شو**» نام دارد (تنظیمات،
   و LuCI؛ پیش‌فرض روشن) و از همان‌جا خاموش می‌شود. سوییچ اصلی LuCI خودِ VPN است: روشن = وصل به کانفیگ انتخاب‌شده،
   خاموش = قطع. **آخرین فرمان برنده است:** هر اتصالی که خودت می‌زنی همان لحظه که
   هسته‌اش بالا آمد (پیش از گیت‌وی) به‌عنوان «وصل بمان» ثبت می‌شود؛ اگر از A به B بروی و گیت‌وی B بالا نیاید، روتر همان
   موقع قطع می‌ماند و در بوت بعدی **B** را امتحان می‌کند، نه A را.
5. اگر وسط کار `sing-box` یا هستهٔ `xray` بیفتد (کمبود حافظه، کرش)، سرویس خودش گیت‌وی را دوباره می‌سازد و تا وقتی قطع
   نکرده‌ای تلاش را ادامه می‌دهد — حتی اگر «اتصال مجدد با تغییر شبکه» خاموش باشد. اگر بلافاصله بعد از هر بازسازی دوباره
   بیفتد (کمتر از دو دقیقه)، فاصلهٔ بازسازی‌ها بیشتر می‌شود (۲، ۵، ۱۵، ۳۰ ثانیه و بعد هر دقیقه) تا روتر در یک حلقهٔ
   کرش گیر نکند. گیت‌ویی که بالا نیاید «اتصال ناموفق» است، نه «وصل، فقط پروکسی».
6. کانفیگی که روی هستهٔ sing-box تنظیم شده، روی روتر با Xray اجرا می‌شود (sing-box بستهٔ پورت ۵۳ را جواب نمی‌دهد و شبکه
   DNS نخواهد داشت) — لاگ همین را می‌گوید.
7. صفحه‌ای که وقتی تونل بالاست باز (یا از پس‌زمینهٔ گوشی برگردانده) شود، «متصل» و زمان درست را نشان می‌دهد — وضعیت از
   `app:init` و از اولین رویداد هر اتصالِ events می‌آید. دکمهٔ وصل روی اتصالی که همین حالا بالاست کاری نمی‌کند (قبلاً یک
   بازسازی ۲۰–۴۰ ثانیه‌ای بی‌دلیل بود). وقتی هسته یا sing-box بیفتد، در تمام مدت بازسازی «اتصال مجدد… (تلاش n)» می‌بینی،
   نه «قطع شده».
8. تغییر شبکه (آدرس WAN عوض شود، PPPoE قطع و وصل شود، prefix IPv6 بچرخد) دیگر خودبه‌خود گیت‌وی را خراب و دوباره
   نمی‌سازد: بعد از ۱۰ ثانیه آرامش، سرویس از داخل تونل یک HTTP 204 می‌گیرد (دو بار، ۵ ثانیه فاصله) و فقط وقتی جواب نگیرد —
   یا اینترفیسی که xray به آن بسته شده ناپدید شده باشد — بازسازی می‌کند. لاگ می‌گوید `Network changed (…) — the tunnel
   answers, kept` یا `… rebuilding`. تغییرهای سمت LAN اصلاً حساب نمی‌شوند.

## کیل‌سوییچ (از v1.16)

تنظیمات → **کیل سوییچ** (هم در UI وب، هم در LuCI). **فقط وقتی VPN قرار است روشن باشد** کار می‌کند — یعنی خودت وصل
کرده‌ای (یا بعد از بوت خودش برگشته) — و تونل بالا نیست: sing-box افتاده، گیت‌وی دارد بازسازی می‌شود، سرور عوض می‌شود،
سرویس کرش کرده، یا روتر تازه بوت شده و هنوز وصل نشده. در این فاصله دستگاه‌های شبکه اینترنت ندارند (reject، نه drop:
مرورگر فوراً خطا می‌دهد و معطل نمی‌ماند). هیچ‌وقت بسته نمی‌شود: دستگاه‌های «مستقیم» (با MAC)، ترافیک داخل شبکه
(LAN↔LAN، مهمان↔LAN، صفحهٔ مودم ISP)، جوابِ اتصال‌های ورودی (port forward)، و ترافیک خودِ روتر (NTP، opkg، سرورها،
رلهٔ ریموت). **قطع کردن VPN** — دکمهٔ قطع، سوییچ LuCI، یا «VPN را خاموش کن» روی بنر — کیل‌سوییچ را برمی‌دارد و شبکه
مستقیم می‌رود؛ خاموش کردن خودِ تنظیم هم همین‌طور. UI و LuCI وضعیتش را می‌گویند (فعال / در حال بستن).

پیاده‌سازی: یک جدول nft جداگانه، `inet irnetfree_ks` (جدول گیت‌وی `inet irnetfree` با هر بازسازی پاک می‌شود؛ این یکی
نه)، اعمال اتمیک (`nft -c -f` و بعد `nft -f`)، و فایل `/etc/irnetfree/killswitch.nft` که سرویس هنگام فعال شدن می‌نویسد
و `/etc/init.d/irnetfree-ks` (START=19، قبل از network) هنگام بوت بارگذاری می‌کند — پس بعد از ریبوت، پیش از این‌که
هیچ اینترفیسی بالا بیاید، شبکه بسته است تا تونل برگردد. از SSH:

```sh
/etc/init.d/irnetfree-ks stop        # جدول را برمی‌دارد (تا بازسازی بعدیِ سرویس، که دوباره می‌گذاردش)
nft list table inet irnetfree_ks     # هست یا نه، MACهای مستثنا
nft list chain inet irnetfree_ks lanblock # شمارندهٔ reject: چند بسته بسته شده
```

حذف بسته (prerm) جدول و فایل را هم پاک می‌کند.

چند چیز که باید بدانی:

- **نام‌ها هنوز حل می‌شوند.** وقتی کیل‌سوییچ شبکه را بسته، DNS دستگاه‌ها به dnsmasq روتر می‌رسد و روتر — که هیچ‌وقت
  بسته نمی‌شود — آن را از ISP می‌پرسد؛ یعنی نام حل می‌شود ولی اتصالِ بعدش رد می‌شود. همان نشت DNS کلاسیک هر
  کیل‌سوییچی؛ پذیرفته‌شده، چون ترافیک خودِ روتر عمداً آزاد است.
- **به‌روزرسانی درجا (`opkg upgrade`) مثل `/etc/init.d/irnetfree stop` است:** prerm جدول و فایل را برمی‌دارد و تا
  سرویسِ تازه بالا بیاید و از «وصل بمان» دوباره فعالش کند (چند ثانیه تا یک دقیقه روی AC-1304) شبکه مستقیم می‌رود.
  به‌روزرسانی انتخاب خودت است؛ اگر این فاصله مهم است، اول VPN را قطع کن.
- **IPv6 دستگاه‌ها وقتی تونل بالاست از تونل می‌رود — حتی با IPv6 خاموش در تنظیمات.** تونل همیشه یک آدرس و مسیر
  پیش‌فرض v6 دارد (همین است که نمی‌گذارد v6 از کنار تونل به WAN نشت کند) و کیل‌سوییچ هر چیزی را که به `IRNetFree`
  می‌رود قبول می‌کند؛ پس کیل‌سوییچ v6 را فقط وقتی رد می‌کند که v4 را هم رد می‌کند: تونل پایین است. با IPv6 خاموش،
  هستهٔ ما به پرسش‌های AAAA هیچ آدرسی نمی‌دهد، پس دستگاهی که نام‌ها را از روتر می‌پرسد با v4 وصل می‌شود؛ فقط آدرس v6
  مستقیم (یا AAAA از DoH خودِ دستگاه) وارد تونل می‌شود، و این‌که به مقصد برسد به سرور بستگی دارد.
- **بعد از ریبوت با «با روشن شدن روتر وصل شو» خاموش**، VPN خاموش می‌ماند و کیل‌سوییچ هم فعال نمی‌شود (نه در بوت،
  نه بعدش) — تا خودت وصل کنی. همین‌طور اگر کانفیگِ ذخیره‌شده دیگر وجود نداشته باشد: سرویس می‌گوید و فعال نمی‌کند.
- سرویس هر ۳۰ ثانیه از کرنل می‌پرسد جدول هنوز هست یا نه؛ اگر چیزی (`fw4 flush`، `nft flush ruleset`، postinst یک
  بسته) پاکش کرده باشد، با یک هشدار در لاگ دوباره می‌گذاردش — و تا آن موقع در وضعیت «فعال» نمی‌گوید.

## دسترسی از بیرون خانه (از v1.16)

**کجاست:** فقط در LuCI — **LuCI → Services → IRNetFree → Remote access** (در LuCI فارسی: سرویس‌ها → IRNetFree →
دسترسی از راه دور). UI وب روی پورت 6969 چنین بخشی ندارد. راهنمای کامل و قدم‌به‌قدم: [`docs/remote.md`](remote.md)
(اول انگلیسی، بعد فارسی).

دو راه، جدا از هم — هر دو می‌توانند هم‌زمان روشن باشند و هر دو به همان UI وب IRNetFree روتر می‌رسند:

1. **رلهٔ خودت (راه اصلی).** رله سرور خودِ توست؛ IRNetFree رله‌ای نمی‌دهد. **اول باید رله را مستقر کنی** — `relay/`
   همین مخزن، روی هاربورا یا هر سرور داکر پشت TLS (remote.md بخش ۱) — **وگرنه این بخش هیچ‌وقت فعال نمی‌شود:** توکن
   دستگاه فقط از رله می‌آید، و LuCI «فعال» بدون آدرس رله و توکن را ذخیره نمی‌کند. بعد در صفحهٔ رله Routers → **Add
   router** را بزن؛ توکن ۴۳ کاراکتری دستگاه را **فقط یک بار** نشان می‌دهد. در LuCI، بخش «رلهٔ خودت»: آدرس رله
   (`https://…`، بدون مسیر)، نام روتر، توکن دستگاه، تیک «فعال»، و دکمهٔ **«ذخیره»** پایین صفحه. خط «وضعیت» در چند
   ثانیه «در حال اتصال…» و بعد «آنلاین (مستقیم)» می‌شود.
2. **تونل کلودفلر (راه دوم).** دکمهٔ «نصب» همان صفحه `cloudflared` فید را نصب می‌کند (چند دقیقه؛ حدود ۳۰ مگ RAM). در
   داشبورد کلادفلر یک تونل بساز، نام عمومی‌اش را به `http://127.0.0.1:6969` بفرست و با Cloudflare Access ببندش
   (remote.md بخش ۲)، بعد توکن تونل را بچسبان، تیک «فعال»، «ذخیره». بدون cloudflared نصب‌شده و توکن، چیزی اجرا نمی‌شود.
   اگر راه مستقیم به کلادفلر بسته باشد این راه پایین است — جایگزینی از داخل VPN ندارد.

- تغییرهای این صفحه **فقط با دکمهٔ «ذخیره» پایین صفحه** اعمال می‌شوند — برخلاف Overview که هر کلیدش همان لحظه اعمال
  می‌شود.
- لینک کنترل از تونل VPN نمی‌رود (رله فقط وقتی راه مستقیم بسته است از داخل تونل وصل می‌شود) و کیل‌سوییچ هم جلویش را
  نمی‌گیرد — ترافیک خودِ روتر است.
- وضعیت و خطاها: خط «وضعیت» همان صفحه، و `logread -e irnetfree | grep -E 'remote:|cloudflared'`.

## چک کردن روی دستگاه (چیزی که CI نمی‌تواند ببیند)

```sh
logread -e irnetfree | tail -50      # همهٔ خط‌های سرویس (از v1.16 هر خطی با irnetfree: شروع می‌شود — بنر و خطای کشنده هم)
dmesg | grep -iE 'oom|killed process'   # هسته‌ای که ناگهان «افتاد»: کار OOM killer بوده؟ (روتر ۵۱۲ مگی)
ip link show IRNetFree               # دستگاه تونل بالاست؟
ip rule show | grep -E '2022|8997|8998|8999'   # قواعد sing-box، استثنای ریموت (8997) و قاعدهٔ استثنای دستگاه‌ها
nft list table inet irnetfree        # MACهای مستقیم
nft list table inet irnetfree_ks     # کیل‌سوییچ (اگر فعال است)
```

- **LuCI → Services → IRNetFree → Log**: ۵۰۰ خط آخر سرویس با علت هر تغییر وضعیت (`status: connected (cause=user …)`،
  `reconnecting (cause=recovery …)`) و حافظهٔ همان لحظه (MemAvailable و RSS هسته‌ها). **Copy diagnostics** همه را با
  وضعیت، نسخه‌ها، حافظه و `ip rule` یک‌جا می‌دهد — بدون توکن و بدون رمزها؛ همین را برای گزارش بفرست.
- اگر سرویس به خطای پیش‌بینی‌نشده بخورد، منظم بیرون می‌آید (`irnetfree: [fatal] …` در `logread`) و procd بی‌نهایت بار
  دوباره بالایش می‌آورد (`respawn 3600 5 0`)؛ اتصال خودش برمی‌گردد.

- گوشی بدون هیچ پروکسی → سایتِ فیلترشده باز شود؛ `ipwho.is` IP سرور را نشان دهد.
- دستگاهِ تیک‌خورده → IP واقعی خودت.
- `free -m` قبل و بعد از اتصال: مصرف RAM را گزارش کن؛ CI فقط در QEMU اندازه گرفته.

## DNS و نشت

- هر بستهٔ پورت ۵۳ دستگاه‌های شبکه — به dnsmasq روتر، یا از خودِ دستگاه به هر resolverی، **resolver داخلی (مثل
  شکن) هم** — و هر پرسشی که dnsmasq به بالادستش می‌فرستد، **وارد تونل می‌شود و هستهٔ خودمان جواب می‌دهد** (DoH از
  داخل تونل). از v1.13.5 حتی وقتی resolverی که DHCP داده روی زیرشبکهٔ WAN است (مودم ISP)، که قبلش مستقیم می‌رفت.
- در حالت «دور زدن ایران» فقط **خودِ هسته** دامنه‌های ایرانی را مستقیم از resolver داخلی می‌پرسد (از WAN، بیرون از
  تونل) — پرسشِ خودِ هسته، نه بستهٔ یک دستگاه. تا v1.16.0 این‌طور نبود: آدرس آن resolverها برای **کل شبکه و روی هر
  پورتی** از تونل مستثنا می‌شد؛ اگر بالادستِ dnsmasq (DNSای که WAN گرفته) یا DNS یک دستگاه یکی از آن‌ها بود — مثلاً
  شکن، یا 8.8.8.8/1.1.1.1 که از بکاپ دسکتاپ به «DNS مستقیم» آمده — پرسش‌ها رمزنشده از ISP می‌رفتند و ممکن بود جوابِ
  فیلترشده (10.10.34.x) بگیرند. از v1.16.1 هیچ بستهٔ دستگاهی به آن آدرس‌ها از کنار تونل نمی‌رود.
- تنها استثنا: DoH/DoT خودِ دستگاه — پورت ۵۳ نیست، رمزشده است، و آن هم از تونل می‌رود.
- تست روی روتر — هر دو باید `dev IRNetFree` بگویند (یک بررسی از خودِ روتر چیزی دربارهٔ دستگاه‌ها ثابت نمی‌کند):
  - پرسش‌های خودِ روتر (dnsmasq): `ip route get <IP مودم یا هر resolver> ipproto udp dport 53`
  - پرسش یک دستگاه: `ip route get <IP هر resolver، داخلی هم> from <IP یک دستگاه LAN> iif br-lan ipproto udp dport 53`

## سرعت

مسیر روی روتر: tun → sing-box → SOCKS → xray → TLS → WAN؛ روی Cortex-A7 هفتصد مگاهرتز **سقفش CPU است** و آپلود
زودتر نشانش می‌دهد. برای دیدن: روی گوشی تست سرعت، همزمان روی روتر `top` — اگر `sing-box` یا `xray` روی ۱۰۰٪ یک هسته
هستند، سقف همین است. چیزهایی که کم‌هزینه‌تر شده: GSO روی tun، بدون access-log مگر در سطح لاگ info/debug، آمار هر ۳ ثانیه،
و **رد کردن QUIC (UDP 443) از شبکه** (تنظیمات → اجازه به شبکه محلی؛ پیش‌فرض روشن) تا مرورگرها فوراً TCP بزنند که هر
پروکسی‌ای حمل می‌کند. برای مقایسهٔ منصفانه: همان کانفیگ روی لپ‌تاپ چه سرعتی می‌دهد؟ اگر لپ‌تاپ هم همان است، سرور/ISP
است نه روتر.

## چه چیزی هنوز نیست

- **failover خودکار** به سرور دیگر وقتی سرور فعلی مُرده (مثل auto-switch در PassWall): دکمهٔ Test و وضعیت نشانش
  می‌دهند، ولی خودش عوض نمی‌کند.
- سرور متفاوت برای هر دستگاه؛ روترهای کوچک؛ بسته‌بندی `apk` برای OpenWrt 25.

## حذف

```sh
/etc/init.d/irnetfree stop
opkg remove irnetfree
rm -rf /etc/irnetfree                      # داده‌ها و هسته‌ها
for s in $(uci show firewall | sed -n 's/^firewall\.\(irnetfree[^.=]*\)=.*/\1/p'); do uci -q delete firewall.$s; done
uci commit firewall; fw4 reload
```
