# v1.14.0 — the connection stays up: a deep audit of every platform, fixed

A read-only audit of v1.13.5 on every platform found about 75 defects. This release fixes the critical
and high ones, plus the medium ones that break a connection, advanced routing, a chain or WireGuard, on
Windows, macOS, Android and the OpenWrt router. It also fixes two things the owner reported during the
work: the DNS leak on a second Windows machine, and a LAN → Wi-Fi switch that broke the tunnel until a
reboot.

## Windows: the DNS leak and the network switch

- **Why names still leaked.** The leak guard pointed every physical adapter's DNS at the tunnel peer
  (172.19.0.2). That address is on-link only while the TUN adapter exists. During every reconnect after a
  network change or a wake, after a crash, and after the app was killed, the peer routed out through the real
  NIC, so every lookup went to the ISP in clear text — and Iranian ISPs answer port 53 wherever it is sent, so
  a leak test showed their resolver. The guard now holds physical adapters on **loopback (127.0.0.2 / ::1)**:
  nothing asked there leaves the machine, with or without the tunnel. The TUN adapter keeps its own
  resolver. IPv6 is always held (the 2026-09-12 leak shape); one adapter that refuses no longer unguards the
  rest; Hyper-V and Bluetooth adapters are guarded; an adapter that appears mid-session is picked up.
- **The server's own name is pinned.** With the adapters on loopback, xray resolving its own server's
  hostname through Windows would ask the tunnel for the address of the tunnel. Every entry server named by a
  hostname is now resolved before the tunnel and the guard come up and handed to xray's own `dns.hosts`
  (`sockopt.domainStrategy` on those outbounds). The address, SNI and Host stay the name. A recovery with
  nothing resolvable uses the last good answer. The same fix closes the router's DNS loop.
- **No dead IPv6 resolver on the tunnel** with managed DNS off (sing-box set one nothing answers).
- **LAN → Wi-Fi.** The default gateway was picked by route metric alone, so after a switch it could name the
  LAN that had just gone away and bind xray to a dead NIC — "restored", yet nothing passed. It is now the
  connected interface Windows really routes by (route + interface metric, never our own adapter), re-read on
  every connect. tun2socks' server routes are journaled (boot-stamped) and removed by exact match, so a switch
  or a killed app no longer leaves a /32 on the physical NIC until a reboot.

## Windows and macOS: staying connected

- **One instance.** A second launch (shortcut, logon task) used to "repair" the first one's live tunnel,
  guard and kill switch. It now brings the running window forward and touches nothing.
- **A dropped connection comes back by itself.** An xray, sing-box or tun2socks that exits on its own is
  rebuilt under the kill switch (bounded: three drops in five minutes, then the banner). The block is lifted
  once the connection is really back — including when the drop landed inside a connect of your own.
- **The system proxy is journaled.** What was there before (a corporate proxy included) is recorded before
  the first change and put back exactly on disconnect, quit, crash (at the next launch) and Windows
  shutdown; the port decides whose a leftover is, so another client on 10809 is left alone. The proxy stays up
  through a settings rebuild. A stuck PowerShell can no longer freeze connect, disconnect or quit.
- **Shutdown, restart, log-off** tear down (session-end / powerMonitor). A stale `activeServerId` is cleared
  at launch. Non-ASCII adapter names are read correctly (UTF-8 PowerShell). The window only shows its own
  page; `open:external` hands the OS http(s) only. Allow LAN is limited to private networks and the local
  subnet. IPv6 privacy-address rotation and VM bridges no longer trigger a rebuild.
- **A held guard no longer outlives a switch to proxy mode.**
- **macOS:** recovery is no longer blocked by a reused PID or a silent native service, DNS stays on the
  tunnel across a reconnect, a failed setup leaves no journal or lock, values from user-owned files reach root
  scripts only as validated IP literals, start-at-login opens hidden.

## Subscriptions, chains, advanced routing (desktop and router)

- **Server ids survive a refresh.** Every hourly refresh used to give a subscription's servers new ids, so
  `activeServerId`, chains, pool entries and advanced-routing targets pointed at nothing — recovery failed with
  "Server not found" and a rule could silently fall to `direct`. Servers are now matched by their link; a
  refresh carries only the fields you were recorded editing (a clean IP you swapped in, a rename, a fragment),
  everything else follows the panel, and an older parser's mistakes are repaired instead of kept.
- A chain that lost a member refuses to connect, by name, instead of collapsing to its last hop. An
  advanced-routing default that no longer exists is an error, never a silent `direct`.
- A refresh that returns nothing keeps the list; responses are capped (8 MB, 60 s, no https → http).
- Edits keep the TCP HTTP header; httpupgrade and raw+http links keep path and Host; SS-2022 plain-userinfo
  links import; the chain latency test measures the whole chain; IPv6 is bracketed in share links and
  WireGuard endpoints; unsupported schemes are reported; imported backups are validated and every value the
  UI renders is escaped.

## OpenWrt router

- The gateway comes back after a power cut or a restart, and stays the way the user left it (a disconnect by
  hand survives a reboot).
- A malformed request from any LAN host (`GET //x:99999/`) can no longer crash the service.
- A dead sing-box or xray is rebuilt, with a backoff that also covers a core that dies right after each start;
  a failed gateway is a failed connect (retried), never a silent "proxy only" that sends the LAN direct.
- Orphaned cores from a killed run are swept; rule 8998 stays while the tunnel device exists.
- Guest and other zones that forward to `wan` reach the tunnel; configs on the sing-box core run on Xray
  (it has no DNS hijack); warnings and state changes go to syslog, and the token no longer does.

## Android

- Always-on VPN / "block connections without VPN" starts the tunnel after a reboot or a process kill;
  a crash loop backs off and keeps trying.
- Cancelling "Connecting…" really cancels; a second connect never leaks the old core; errors stay on screen.
- The tunnel's local SOCKS/HTTP proxies ask for a per-session password; the metrics listener is gone.
- The per-app picker sees your apps on Android 11+ and never lists IRNetFree itself.
- Subscriptions added from "+" really import; a failing one is no longer refetched forever; ids survive a
  refresh as on the desktop.
- Editing a VLESS Vision server keeps `flow`; blank `sni`/`fp` fields fall back like the desktop; line-wrapped
  base64 subscriptions decode; `host:2053/` keeps its port; a `+` in a WireGuard key stays a `+`.
- A WireGuard test by hostname resolves the endpoint first (the corporate endpoint could crash the app);
  tests and ⚡ fastest follow Settings → Default core; ⚡ never picks a server it just measured as dead.

## Behaviour you will notice
- On Windows, while connected in TUN mode, `ipconfig` shows the physical adapters' DNS as 127.0.0.2 / ::1.
  That is the hold; the tunnel adapter answers. With managed DNS off the tunnel adapter lists `::1` for IPv6
  on purpose.
- If a subscription moves a chain member to another address, that member comes back as a new server and the
  chain refuses to connect, by name, until you pick it again. v1.13.5 silently dialled the chain's last hop
  from your ISP instead.
- On Android the tunnel's own 127.0.0.1:10808/10809 now ask for a per-session password; anything else pointed
  at them is refused. Use the Pool's ports to share the tunnel with other apps.
- Edits you made to a subscription server before this version were never recorded, so the first refresh after
  updating takes the panel's values for them once; edit again and they are kept from then on.
