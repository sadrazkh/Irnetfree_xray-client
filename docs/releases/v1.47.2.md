# v1.47.2 — a reload leaves no dead or stray core, and a shutdown ends everything

By the version rule: fixes to what already exists, so the third number goes up. Desktop, headless service and router;
Android is the same code as v1.47.1.

## Where it came from

Nobody reported these. The first two were found by reading the code while a CI failure was being traced on 2026-11-10
(a test run that never ended), the third while the second was being fixed. Each is proven with the test fakes, every
test seen failing before its fix. **Nothing here has run on a router, in Electron or against a real core.**

## A core that died while the app was reloading it (desktop and router)

A reload restarts only the core and leaves the tunnel alone. The app asks for one when a routed app reaches new
destinations, a group member is set aside or comes back, an internet reaches its data cap, the LAN users change, the
hello cut switches on, or the router has taken new geo files at night. Before the restart it checks the new config
with a core process of its own, which takes a moment: seconds on a router.

A core that died by itself in that moment was taken for the restart's own stop. Nothing rebuilt it, the reload stood
down without a word, and the tunnel went on sending everything into a closed port while the window said connected.
On a router the tunnel watchdog rebuilt it some minutes later (it asks every three minutes, and again a minute after
a miss). The desktop has no such watchdog (KI-046).

- **That death is now a drop like any other.** The kill switch (when it is on) and the rebuild start at once, and the
  reload gives way to them. The reload's flag goes up only for the restart itself, after the check.

## A Disconnect that came while the core was being restarted (desktop and router)

A restart stops the old core and starts the new one once the old one has exited. A Disconnect that landed in that gap
ended the old core only. The new one then came up and stayed: "disconnected" on screen with the SOCKS and HTTP ports
still open, and a log line saying the core had reloaded, until the next connect or the exit (KI-047).

- **The reload ends the core it started** when the connection was ended meanwhile, and says nothing about a reload.
  A connect made since is left alone: the core is its own.
- On the router and the headless service, a new core that such a stop ended inside its first second is no longer
  logged as "the core did not come back, rebuilding the connection".

## A shutdown that did not end what was in flight (router and headless service)

`shutdown()` stopped what ran, but a rebuild already half-way was not told. Its attempt failed on the core the
shutdown had stopped, it waited its backoff and connected again: a core and a gateway up after the service had been
told to stop. In the app the process exits within three seconds of the shutdown and the exit hook cleans up (read,
not run). In the tests it kept a whole run from ending, which is what the hour-long CI job of 2026-11-10 was (KI-045).

- **A connect or a rebuild caught half-way gives way** and stops what it started.
- **A Connect or a Reconnect that arrives after the shutdown starts nothing.**
- **The connection stays the one the next start resumes.** A shutdown is not a Disconnect: the router comes back
  connected as before.
- The two network watchers no longer keep the process alive by themselves.

## Limits

- The desktop's Quit is unchanged. A core that a connect or a reload starts in the quit's last moment is still ended
  by the exit hook, not before it.
- That the real core manager orders a start and a stop the way the tests hold them is read from `xrayManager.js`,
  not run.

## Tested

- `npm test`: 3279 tests, none failing, 9 skipped for what this machine lacks (a browser, POSIX signals, macOS).
- `tests/serviceGateway.test.js`, where the router's connect, recovery and shutdown run over the fakes: 132 runs, six
  at a time, no failure and none that hung. A file whose test fails half-way through a rebuild used to hang for good;
  it now ends in a second.
- The desktop's `rebuildActiveConfig` runs from its own source over a fake core (`tests/desktopLifecycle.test.js`).

## Owed

A router and a desktop in normal use. Nothing to do by hand: if a connection ever stays "connected" with nothing
passing, or a port stays open after a Disconnect, the log of that moment is what the next round needs.
