# v1.20.0 — Routing profiles, "via a base", the flow tree and share links

## What the owner asked for

Parts two and three of his 2026-10-08 request (part one, JSON configs, shipped as v1.19.0):
- several saved advanced routings;
- one config that reaches everywhere, with other targets riding on it — as an option, with today's chains kept as they
  are;
- a picture of where traffic goes that anyone can read and change;
- advanced routing and chains copyable as one link that carries everything needed;
- nothing broken.

## Routing profiles (every platform)

- **Several advanced routings.** Each profile has its own rules, default, "apply the routing mode too" and an optional
  base. Servers, chains and bases are shared between profiles.
- **Today's routing becomes the first profile**, «روتینگ ویژه» / "Advanced routing", on first start. The old settings
  keys keep mirroring it, so an old backup, an older app on the same data and Android's legacy reader still see it.
- **The home picker** has one 🧭 row per profile that has rules or a default. A plain advanced selection (an old
  selection, LuCI, the router's boot intent) means the first profile; ★ Make default moves a profile there.
- **Tabs** on the routing page: rename, ★ Make default, Duplicate, Copy link, Delete (the last profile cannot be
  deleted).
- **Reconnect needed** is now raised when the live profile or a chain it uses changes, as a server edit already did.

## Via a base

- **Per rule and for the default**: inherit (the profile's base, if any), none, or any server or chain. Direct and
  block never ride on anything.
- **One base, shared.** A base is built once (`base-<id>`, a chain base as its hops) and every target through it dials
  through it (`sockopt.dialerProxy`). A target used without a via keeps its own outbound, unchanged.
- A target never rides on itself: when the via (or the inherited base) is the target, it dials directly.
- A JSON server through a base: its own helper dialer is replaced, as for a chain's later hop.
- **Mux** stays on direct server targets only; a base and anything through it get none.
- **Entry addresses** — the TUN bypass, the strict guard's holes and name pinning — use the base's address, not the
  target's.
- **A base that is gone** (a deleted server, an emptied chain) refuses the connect with a plain message; the rule is
  marked on the routing page.

## The flow tree

- **Per profile**: rules → targets → bases, each base drawn once with every target through it pointing at it; the
  default as "everything else". Mirrored in Persian.
- **Clickable**: a rule opens its row, a server its edit form, a chain its card; anything gone is drawn in red with
  its reason.
- **Live speed** on each branch while that profile is connected (desktop and the router's web UI).
- **Home**: the small path shows "via <base>".
- **Android**: the same tree as a vertical list.

## Share links

- **Copy link** on a profile and on each chain card: `irnetfree://routing/…` (raw deflate + base64url, one line). It
  warns first that the servers it uses are inside, in full. A QR when the link is 1,700 bytes or less.
- **What it carries**: the profile (rules, default, vias, base, "apply the routing mode too"), the chains it uses and
  every server they need. Nothing else of the sender's settings.
- **Import**: paste it into the add box (or scan it on Android). A preview lists the name, rules, chains, the servers
  already here, the new ones and anything unreadable, then Import:
  - servers already here (same identity) are reused; new ones are added by hand, not as a subscription;
  - a chain with the same name and members is reused;
  - the profile is added as new, renamed "Name (2)" if the name is taken.
- **Refused, with nothing written**: a broken, cut, oversized (over 64 KB unpacked) or unknown-version link.
- Android and desktop read each other's links (a shared fixture pins the format).

## Android: a gone target, as on the desktop

- A rule whose server or chain no longer exists is left out: its traffic follows the default. Before, Android sent it
  direct without a word.
- A default that no longer exists refuses the connect, with the reason. Before, Android connected and sent everything
  direct while showing "connected".
- A chain imported with a server this phone cannot read stays unusable (marked), never shorter: a shorter chain would
  dial the rest straight from the phone.

## The router

- The web UI has everything the window has.
- LuCI's connect list has one item per profile.

## Unchanged

Servers, subscriptions, the simple routing modes, the pool, chains used without a via, JSON servers and mux. A config
built from today's settings is byte-identical to v1.19.0 (169 cases checked).

## Check on your own devices

- Make a second profile with a base and one rule through it, connect it, and watch the tree's live speed.
- Copy its link, paste it into another install (or the phone) and import it.
- On Android: the routing screen, a connect through a base, scanning a routing QR.
- On the router: LuCI's list, and a connect of the second profile from the web UI.
