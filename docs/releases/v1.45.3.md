# v1.45.3 — A config behind a VPN router works again

By the version rule: fixes and improvements to what already exists, so the third number goes up.

## What the owner reported

With the router's VPN on, a site would not open under advanced routing on his laptop, his other configs answered "as if nothing happens", and a simple config worked. He said it worked before, on both the patterniha core and the normal one, and refused the workaround of leaving the laptop out of the router's VPN. He also asked why a tunnel should care what is inside it.

## What was really happening

A tunnel hides traffic from the ISP, but its far end reads what comes out. Every server of his measured (`exit-sniff`, one at a time, with the name inside the tunnel) has sniffing on without Route Only, so it reads the name in a TLS hello and dials that name instead of the address. A device's own config inside the router's tunnel then reaches the real site its name stands for: a Reality or pinned config dies, a `ws` one whose name is its own server lives.

Advanced routing was never the cause. Measured on the same path: one server gives the same result in simple and advanced mode, and the two write the same outbound. His advanced plan used pinned and Reality servers, his simple one a `ws` one. The same plan as v1.43.0 wrote it dies the same way, so no change in the app's config is behind it.

**Not established:** what changed on the path recently. The router's sniffing, its exit server or that server's panel could each be it, and the fix does not depend on which.

## What changed

- **`src/main/helloCut.js`:** Xray's sniffer wants the whole hello in one TLS record. Cut into several it reads nothing, the address stands, and the far side takes the records as usual. Interval 0 writes them in one go, so a connection opens no later.
- **On evidence only.** At a connect with no tunnel of ours up, two public addresses are asked for another site's name. A certificate naming that site proves something dialled the name. Answered as themselves: nothing changes, and the config is the same to the byte. No answer: the last answer stands. A route that dies under a live connection turns it on once, with a reload.
- **Left alone:** a config with its own fragment, noise, final mask, dial mode or ECH, and any hop behind another. Each keeps its own in a mixed plan.
- **Tests and pins:** pings cut as the live core does, also under our own TUN, whose exit may read names too. While the path reads, no certificate is learned or dropped, since it would be the real site's.
- **▶ on the routing page and on every row of the Home picker.** It starts that routing or config as a config's card does. *Corrected in v1.45.5:* this said the tunnel stays up on a switch. It does not: the tunnel is rebuilt for the new plan, and an armed kill switch seals the gap. Chains already had one on their card.
- **The warning** (`src/main/routeWatch.js`): while connected a small request goes through the local port; two misses and a line under the state says which route is dead and what to do, until it answers. Names go through the default too, so a dead default stops every site, not only those without a rule.

## A correction to v1.45.2

v1.45.2 blamed the router's own core. Its test could not tell the router from the server it leaves by. That change is right but covers only the router's core; this one covers any hop.

## Measured

- **His profile, on a throwaway core, the path as it is:** hellos whole: nothing answers. Cut: web 204 by address and by name, `rain.tes.ca` 200 in 1.4 s, `claude.ai` reached, the corporate WireGuard through the pinned base answered DNS. The domain rules' target had to move from `IRbaUK7`, whose address does not open TCP on this path at all, to `IRbaUK2`.
- **Single servers, official core and patterniha:** pinned and Reality dead whole, alive cut, company site under 3 s.
- **`scripts/probe-hello-cut.js` (CI, both suggested cores):** a real core in the middle with sniffing on: pinned and Reality die with the real site dialled; cut they pass and the real site is not dialled.
- **`tests/helloCut.test.js`:** what takes the cut, byte-identical off, one mixed plan, the check, the router's service.

## Limits and owed

- **Not run in the real app under TUN**, on the router or on a phone.
- **A chain's second hop** dies behind a server that reads names, and cutting it brought it back in a manual test (three pairs). Not in this version: it touches the chain relay.
- **A separate WireGuard app on the device** is UDP, has no hello, and was not measured.
- **Android** does not have the cut or the warning yet. **sing-box-engine configs** are not cut, and a dead route on one restarts its core once for nothing.
- **A config with no pin that asks for one to be learned** cannot get it on a path that reads names, since the certificate would be the real site's. It connects once it is on another network.
- **Not cut either:** an XHTTP download leg of its own, and the multi-internet link tests.
- **A false dead route** (a laptop waking) leaves hellos cut until the next connect that finds the path clean. The cost is only that split records go out.
- The warning measures the default route, not each rule's target.
