# v1.7.1 — DNS continuity, session stability and settings

DNS protection now rechecks the active session after DHCP/external DNS changes
and discovers new network adapters. Compatibility backends check every 30s;
the native Mac service scans one service per bounded timer tick and discovers
new services every 30s. Original DNS is journaled before changes and preserved
through repeated repairs. A failed refresh is reported; it does not rebuild a
healthy tunnel. This is eventual repair, not a firewall guarantee during the
interval before detection. Strict protection and existing WebRTC rules remain
unchanged.

A corporate resolver explicitly assigned to a routing target now takes priority
when its IP also appears in a direct/remote resolver list. Ordinary Iran/China
split DNS, chain composition, private routing and advanced rule order remain.

Metrics polling is single-flight, bounded and cancelled on stop. Old-session
responses cannot update current statistics or stall detection. Delayed exits
from old core processes cannot clear a replacement process or falsely report it
stopped. These fix confirmed lifecycle defects; the reported gradual slowdown
and improvement after Get IP are not yet reproduced on a live user connection.
Get IP does not restart or reset the core, and no periodic external probes or
forced reconnects were added.

The home chart now shows a timestamped 60-second window with a shared rate
scale, distinct upload/download lines and responsive high-DPI rendering.
Settings have topic navigation, search, clearer grouping and accessible names,
with Persian/English and RTL support. Existing saved values and handlers remain.

Validation includes the full Node regression suite, real-core config checks,
DNS packet probes and corporate WireGuard HTTP/HTTPS loopback tests. Mac Swift
compilation/validation and release packaging are checked in CI. Real DHCP,
adapter hot-plug and native service behavior still need device acceptance;
loopback probes do not prove every OS/browser DNS path is leak-free.
