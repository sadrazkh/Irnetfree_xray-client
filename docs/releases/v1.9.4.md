# v1.9.4 — Android: a subscription is fetched through a core, connected or not

Android only. Nothing in `src/` changed (`npm test` 796/796).

## What the log finally said

v1.9.3 added a report of who answers for the panel. It answered the question,
and it ruled out everything the previous two releases had assumed:

```
sub.irnetfree.info -> 2a06:98c1:3120::3, 2a06:98c1:3121::3,
                      188.114.99.0, 188.114.98.0 (os);
could not read the certificate (Handshake failed)
```

- **Those are Cloudflare's own addresses.** The name resolved correctly — DNS
  was never poisoned for this host, so v1.9.1's `TrustedDns` fallback and
  v1.9.3's DoH-first resolution were both fixing something that was not broken.
- **The certificate probe failed too**, and that probe runs with verification
  switched off. It cannot fail on an untrusted CA, a wrong hostname or a
  middlebox certificate — it failed because **no certificate ever arrived**.

The TLS connection is being broken before the server can answer, which is what
SNI-triggered interference looks like from inside a client: the ClientHello
carrying `sub.irnetfree.info` goes out in the clear and the connection dies. A
browser gets past it (encrypted ClientHello, or QUIC). The desktop client gets
past it only because its whole system sits inside the TUN, so its fetch was
never on the raw network at all.

## The fix

The phone can do the same thing, and now does: **the fetch goes through a core,
always.**

- tunnel up → the running core's SOCKS inbound (v1.9.1 already did this)
- **tunnel down → a throwaway core on a free port**, exactly as a latency test
  already spins one, torn down as soon as the body is in
- no servers at all → directly, because there is nothing to borrow

That last case is the only one left on the raw network, and it is the only one
where nothing better exists: a brand-new install whose sole content is a
subscription URL. Everyone else — anyone with one working config — now fetches
subscriptions the way the desktop does, without having to connect first.
"Connect first" was never a real answer when connecting is what needs the
subscription.

Also: addresses are tried IPv4 first. The log above listed two IPv6 addresses
ahead of the IPv4 ones, and OkHttp dials them in order — on a phone with no
working IPv6 path that is two timeouts before the address that can work.

## What the earlier releases got wrong

v1.9.1 and v1.9.3 were built on the theory that the network was answering with
a forged address or a forged certificate. It was doing neither. The reason the
theory survived two releases is that the error said "handshake failed" and
nothing else; the diagnostic added in v1.9.3 is what ended it, and it stays.
