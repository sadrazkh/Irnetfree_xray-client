# v1.45.1 — Domain rules that always catch, and company hosts that work with sniffing on

By the version rule: fixes to routing that already exists, so the third number goes up.

## What the owner reported

> Domains I send through another config sometimes go through it, sometimes don't, and sometimes the service does not work at all.

> I am sometimes forced to turn sniffing off: some of the company's hosts only work with it off, others only with it on. Don't remove it: make the company work with it on, on every core, on by default, and still possible to turn off.

## What was wrong, measured on real cores

Under a TUN the core is handed a bare address, and the only name it ever has is the one it reads from the first bytes. With sniffing on, that name also replaces the address. So neither setting could suit every host:

| A connection to | Sniffing off | Sniffing on | Now |
|---|---|---|---|
| a corporate address, its own name | the VPN | the VPN | the VPN |
| a corporate address, a name that resolves elsewhere | the VPN | the default: lost | the VPN |
| a corporate address, a name nobody knows | the VPN | the default: lost | the VPN |
| a wrong public address, a corporate name | the default: lost | the VPN | the VPN |
| a name in a domain rule | the default: lost | its target | its target |
| anything else | the default | the default | the default |

Three more causes, each behind the "sometimes":

- **A star meant nothing.** To the core a `*` is an ordinary character, so `*.claude.com` and `*anthropic.com` matched no name at all.
- **A bare name was a substring.** `x.com` also caught `netflix.com`.
- **QUIC went its own way.** claude.ai publishes HTTP/3. The core cannot read an Initial shaped as Chrome sends it, so the same site went to its target over TCP and to the default over QUIC.

## What changed (desktop, router, Android)

**The company works with sniffing on.** It stays on by default and the switch stays. A saved "off" stays off, and the switch now says what that costs: domain rules do not work in TUN mode. With sniffing on, `sniffing.ipsExcluded` lists the private ranges, every address or range in an IP rule the config really holds, and what a split-tunnel WireGuard of the plan carries. Such an address keeps its route and is never replaced by a name. A range wider than /8 is the internet rather than a host, and is not listed. Everything else is sniffed as before. To keep one host away from sniffing, put its address in an IP rule.

**Poison stays rescued.** Iran's poison answers (10.10.34.34-36) are private addresses, and reading the name is what saves a connection to one. They are cut out of any range around them, so they stay sniffed.

**A domain rule means what it says.**

| Written | Means |
|---|---|
| `example.com`, `.example.com`, `*.example.com` | the name and everything under it, not `notexample.com` |
| `*example.com`, `api.*.example.com` | a wildcard over the whole name |
| `https://example.com/page` | that address's name |
| `google` (no dot) | any name holding the word, as before |
| `domain:`, `full:`, `keyword:`, `regexp:`, `geosite:`, `ext:`, `dotless:` | as written |

This also applies to a LAN user's routing profile. A rule left with nothing readable is dropped, because an empty field would make the core refuse the whole config.

**QUIC follows the name, or falls back to TCP.** With sniffing on, when a domain rule sends something away from the default, two rules go right before the catch-all: QUIC with a readable name goes on as usual, and QUIC whose name cannot be read is refused. A browser then uses TCP, where the name is always read. With no such rule, or sniffing off, QUIC is untouched.

## Limits

- **A core older than the key.** Xray added `ipsExcluded` on 2026-04-13 (XTLS/Xray-core d342361). An older core ignores it and behaves as sniffing on did: official Xray 26.3.27 was measured doing so. Official Xray 26.10.21 and Xray-PattN 26.9.9 and 26.11.1 were measured to honour it, and the suggested cores of both kinds are checked in CI on every run.
- **Sniffing off.** With it off, nothing is read: domain rules do not work in TUN mode, as before.
- **A domain rule on an address in an IP rule.** The name is not read there, so the IP rule wins.
- **Other UDP on port 443.** When a domain rule is in play, anything else on UDP 443 that has no readable name and no IP rule is refused too.
- **ECH.** A site with ECH shows only its cover name (`cloudflare-ech.com`). Use an IP rule for it. claude.ai and api.anthropic.com publish none today.
- **A plain address in a chat app.** A program that dials an address and sends no name has nothing to read. Only an IP rule catches it.
