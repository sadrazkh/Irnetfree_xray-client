# v1.13.3 — OpenWrt: the router stays reachable while the tunnel is up

OpenWrt only. On the owner's Google Wifi (OpenWrt 23.05.4) v1.13.2's proxy
worked, but connecting with TUN took the whole house off the network — the
router itself included — until it was power-cycled. The log showed nothing
after "TUN started on IRNetFree". This release is the cause, the fix, the
guard, and the test that would have caught it.

## The cause

sing-box's `auto_route` rule set on Linux begins with
`9001: lookup 2022 suppress_prefixlength 0`. With a single default route in
its table that rule is harmless (a prefix-0 match is suppressed). But
`route_exclude_address` is always set — the proxy server's own IPs — and with
it sing-tun fills the table with the SPLIT ranges around the excluded
addresses instead of one default route. None of those has prefix 0, so nothing
is suppressed any more, and every packet the router itself sends to a LAN
client — DNS replies from dnsmasq, DHCP, LuCI, the IRNetFree page — is routed
into the tunnel and lost. Forwarded LAN-to-LAN traffic between subnets goes
the same way. The QEMU smoke never saw it: it talks to the service from
127.0.0.1, which the `local` table answers before any of this.

## The fix

One more `ip rule` of ours, at **8998**, before both the MAC bypass (8999)
and everything of sing-box's (9000+):

```
ip rule add pref 8998 lookup main suppress_prefixlength 0
```

Anything the main table can route by a *specific* route — the LAN subnets,
VLANs, the WAN's own network, link-local — stays on main. Only a destination
main would send to its DEFAULT route falls through to sing-box's rules and
the tunnel. That is the split a gateway wants, for the router's own traffic
and for forwarded traffic alike, IPv4 and IPv6. The excluded devices' rule
(8999, marked packets → main) still wins the internet for them afterwards.

## The guard

`TunOpenwrt.verify()` now also runs `ip route get <a LAN address>` (the
router's own address with one bit flipped, from `ubus … network.interface.lan
status`) and refuses to go active — rolling sing-box, the rules and the table
back — if the answer names the tunnel device. A refusal is a line in the log;
going active was the outage.

## The test

The QEMU smoke, on 24.10.2 and 23.05.5, now asserts where packets actually
go after connect: router → LAN client stays on `br-lan`; router → internet
and LAN client → internet go to `IRNetFree`; LAN client → LAN client stays on
`br-lan`; an excluded device (mark 0x1f1e) → internet goes out `eth0`; and
after disconnect the router goes out `eth0` again. Table 2022 is printed for
the record.

## Also

`ip-full` (iproute2) is now a dependency — the installer adds it — so `ip
route get … mark` and `ip rule … suppress_prefixlength` are the real thing on
every image. `src/main/` changed only in `tunOpenwrt.js` and `openwrtNet.js`.
