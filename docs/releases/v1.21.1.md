# v1.21.1 — sing-box 1.14: DNS reaches Xray again

## What the owner reported

Under TUN with sing-box 1.14, a WireGuard's private names stopped resolving ("name not resolved") and DNS leaked.

## Why

- sing-box 1.14.0 added the TUN inbound's `dns_mode`. Under `auto_route` its default is `hijack`:
  - sing-box sets the interface DNS itself;
  - it answers every query to `dns_address` with its own resolver. That address defaults to the one after the TUN's
    own, 172.19.0.2, which is the very peer the app makes the adapter's resolver.
- Here sing-box is only the TUN → SOCKS forwarder, and its config carries no DNS. So those queries never reached Xray:
  - the managed DNS was bypassed;
  - a WireGuard's private resolver was never asked;
  - the rest left through the system resolver.
- «به‌روزرسانی» / Update installs GitHub's latest stable sing-box, which is 1.14.3 now. So every new or updated
  install had it.

## The fix

- **`dns_mode: "disabled"` from sing-box 1.14 on.** sing-box then sets no interface DNS and hijacks nothing, and every
  query goes on to Xray as it did on 1.13.
- **Written by the installed binary's own version** (`sing-box version`, read once per binary). 1.13 refuses the key,
  so its config is exactly the one before.
- **The router always keeps DNS with the app**: dnsmasq is its resolver.
- **A new setting, "DNS in TUN (sing-box)"**, beside the leak guard:
  - "The app" is the default;
  - "sing-box itself" leaves DNS to sing-box's own default, with a warning that it bypasses the app's DNS rules and a
    WireGuard's private names;
  - never under the strict leak guard;
  - a change applies on the next connect.

## Verified on a real TUN (CI)

A new job, `tun-dns` (scripts/tun-dns-probe.js), runs in a network namespace of its own on the GitHub runner, on
sing-box 1.13.14 and 1.14.3. It uses the app's own configs:
- Xray for a corporate WireGuard under TUN with managed DNS;
- the sing-box TUN config.

The checks:
- A WireGuard private name and a plain one, asked of the tunnel's resolver (172.19.0.2), are answered by Xray, and a
  fake ISP resolver on the physical side hears neither.
- On 1.14.3, the v1.21.0 config (no `dns_mode`) is the control: the names never reach Xray — the reported bug,
  reproduced.
- `sing-box check`: 1.13.14 refuses `dns_mode`, 1.14.3 accepts it.

The probe asks over TCP when UDP gets nothing. In the namespace the SOCKS UDP relay does not answer on either version;
the routing decision under test (hijacked or forwarded) is the same for both protocols.

## Unchanged

- Every config on sing-box 1.13 or older, and every Xray config: byte-identical to v1.21.0.
- The ⭐ suggested sing-box stays 1.13.14, the floor. A download installs GitHub's latest stable, 1.14.3, now verified
  with this fix.
- The macOS native backend bundles its own 1.13.14.

## Check on your own devices

- Windows, sing-box 1.14.3, TUN, your corporate WireGuard: an internal name resolves.
- A DNS leak test shows only the tunnel's resolvers.
