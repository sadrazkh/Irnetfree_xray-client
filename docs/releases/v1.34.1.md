# v1.34.1 — a chain carries a closed connection to its last byte

By the version rule: a fix to something that already exists (every chain, base and group through a hop) — the
third number.

## What the owner asked for

The CI job "cores accept the configs" failed now and then in probe-group's two chain rounds only —
`[group → S3]` and `[H → group]`, "no HTTP answer" on both members, at ports 22400+ (so not v1.33.1's
ephemeral-range cause). Find the root cause from the configs and the cores' logs, check whether a real user's chain
loses connections the same way, and fix the app or the probe.

## The cause: the core, through any WebSocket hop

Not the group: a plain chain `[H → S1]` lost the same way, and a raw-TCP hop never did. In Xray, a hop whose
transport ends with an error instead of EOF — WebSocket's close frame always does ("websocket: close 1000") — has the
outbound handler interrupt the in-memory `dialerProxy` pipe to the next hop (app/proxyman/outbound/handler.go), and
an interrupted pipe drops whatever that hop had not read yet (transport/pipe/impl.go). "No HTTP answer" was a small
page dropped whole. Read in the sources of 26.10.21 and current main; nothing upstream fixes it yet.

On a 4-core Linux runner, both cores (Xray 26.10.21, Xray-PattN 26.10.22), servers on 26.3.27 or on the client's
own core:

| through a ws hop                   | small page        | 256 KB page, closed when sent |
|------------------------------------|-------------------|-------------------------------|
| `[H → S1]`, `[H → group]`, `[group → S3]` | 1–4 % lost  | 44–68 of every 100 cut short  |
| a raw-TCP hop                      | none              | none                          |
| through the relay (below)          | none              | none of 2,400                 |

On Windows it shows only under `GOMAXPROCS=1` (one CPU's scheduling) — why the local runs passed. So a real
user's chain through a ws/CDN hop cut short any download or page the server closes when done.

## The fix: a loopback relay between the hops

`configBuilder.relayHopDials`, the last pass of every connect's config (and the pool's): a vless, vmess, trojan or
http dial over a TCP transport through a proxy hop now dials `chain-relay~<hop>` — a SOCKS outbound into one
loopback SOCKS inbound `chain-relay` (127.0.0.1, an account per hop), routed by account to the hop before any other
rule. The bytes are in the kernel before the hop's error, and nothing is dropped.

- Kept as they were: a WireGuard (and any UDP transport, XHTTP over HTTP/3) dialling a hop, a Shadowsocks or SOCKS
  exit (their UDP is UDP), and a hop that is a freedom (fragment / interface dialer), a loopback or a WireGuard.
- The accounts' level has no user counters: a LAN user called `proxy-h0` is not confused with a hop.
- The port: taken with the API's at every connect and reload (`getFreePorts(2)`), desktop and router. A port the
  config already uses, or none: the config of before.
- Android: the same pass in ConfigBuilder.kt, its port picked free like the metrics one, locked with the session's
  random LocalAuth password (another app on the phone can reach a loopback port).
- Latency tests (pings) build without it, as before.

## Good to know

- An official core older than 26.4.25 loses the same tail inside a group's own loopback (it copied through a pipe
  of its own until XTLS/Xray-core#6005): 26.3.27 cut every 256 KB page short through `[H → group]`, relay or not.
  The suggested cores are well past it; a version gate for groups is a separate task.
- scripts/probe-chain-tail.js prints, for the record, how many pages the core still cuts short without the relay —
  when that reads none, the core was fixed and the relay could go.

## Proven

npm test (2747); validate-configs: 437/437 on 26.10.21, 423/423 on PattN 26.10.22, and 26.3.27 accepts the relay
(its 30 refusals are MASQUE, unknown to it); CI on the branch green (12 jobs: cores, Android compile + JVM tests
incl. ChainRelayTest, both OpenWrt QEMU jobs). New CI probe scripts/probe-chain-tail.js on both cores: 40/40 whole
pages per round through the relay. A Linux stress run: probe-group 8 runs × 5/5 rounds and probe-chain-tail
3 × 100 pages per round, both cores, nothing lost.
