# v1.28.2 — Android routing that says what it runs; a group's dead member set aside by the app; battery

By the version rule: fixes and improvements to what exists, so the third number.

## What the owner asked for

"Android's per-app routing and the automatic rules like Bypass Iran don't work right — on Windows and the router
they do; fix it completely"; "anything that makes Android easier on the battery without breaking anything"; "the
multi-config load balancer on the router seems to get into a lot of trouble over time".

## What was found

**Android routing.** The config Android builds was compared with the desktop's, rule by rule: Bypass Iran in simple
mode and under a profile, rule order, domain strategy, sniffing, the DNS plan (the in-country resolver with
`expectedIPs geoip:ir`, DoH on the exit, the port-53 hijack) and the PattN subprocess's geo files are the same. What
differs is around it:
- A change made while connected — the routing mode, the per-app list, sniffing, DNS, the routing profile — was saved
  and shown on Home as if live, but the running tunnel kept what it was built with until the next connect. The desktop
  asks to reconnect (settingsMeta.js); Android said nothing. This fits both reports.
- A server running on sing-box carries none of the app's routing (SingboxConfig has no geo rules), silently.
- App rules made on Windows (`process`) reached the phone in shared profiles and were dropped without a word —
  Android never tells a VPN which app opened a connection.
- Android's Private DNS set to a host sends the phone's lookups around the app's resolver; Bypass Iran then sees
  foreign CDN addresses for some Iranian sites.
- "Block connections without VPN" leaves the apps per-app routing keeps out of the VPN with no internet at all.

**The router's groups.** A soak test with real cores (both suggested: Xray 26.3.27 and PattN 26.9.1) found no leak in
the group itself under load — but the core's health check probing a member whose TLS handshake never completes (a
server that accepts and stays silent, as a filtered one does) leaves one established connection and its goroutines
behind per probe, forever: 3 → 33 in four minutes at a 2 s probe; without TLS the core closes them. At 10 s that is
~360 an hour per dead member — on a router, the "fine for hours, then trouble". The same core bug as the router's
2026-10-05 report (a socket per failed handshake).

## What it does

### Android
- **"Not in the running connection yet"** — Home, Routing and Settings say by name which changes the running tunnel
  does not carry (routing mode, per-app, sniffing, block ads, custom rules, DNS, IPv6, log level, default core, local
  ports, the routing profile in use), with Reconnect now (`SettingsApply.kt`).
- **The connect says its routing** — "Routing: Bypass Iran — Iranian sites go direct, by name (sniffing on) and by
  address", or the profile's rules; a warning when the server runs on sing-box, when Windows app rules are left out,
  and when Private DNS is set to a host (`TunnelSetup.routingNotes`).
- **Per-app** — Home's scope says "whole system" for "only these apps" with none chosen (as the VPN takes it); the
  per-app section says what Android can do (in the VPN or out of it); a warning in the log and under the section when
  "Block connections without VPN" is on.
- **Windows app rules** — shown as "app … — Windows only, skipped here" in the profile's flow.
- **Battery** — the per-second traffic reading, the "connected for" clock and the LAN-sharing address poll run only
  while the app is on screen (nothing else reads them); the speed is per second of time that really passed.

### Desktop & router
- **A group's dead member is set aside by the app** — dead for 90 s while another member answers: the core is
  reloaded without it (its probes, and their leak, stop); the app tests it every 3 min through a throwaway core and
  puts it back when it answers; reloads at least 60 s apart; never the last member that might answer; members dialled
  through a hop are left to the core (`groupEvict.js`, `settings.groupSkip`, `expandGroups(…, skip)`).
- A reload (process routes or groups) now hands the poller the new group map (it kept the old one).

## Not proven here

The Android changes on a device (owner); real WARP+/servers for the groups beyond the loopback soak; Android's own
groups still rely on the core's health check (30 s) — the set-aside logic is desktop and router only.
