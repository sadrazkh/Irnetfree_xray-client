# v1.35.2 — `pcn` is read, and an import says what it did not read

By the version rule: a fix to something that already exists (reading share links) — the third number.

## What the owner reported

«پارامتر pcn اینارو برنامه نمیخونه» — Fastly-fronted XHTTP links with `sni=firefox.com&pcn=default.ssl.fastly.net`
did not connect; the same servers with `pcs` did. Then: «فقط اون 256هش هم که الان خوندئه میشه این خراب نشه».

## `pcn`

Not a standard key — not in Xray's TLS docs nor in v2rayN's share-link code (which writes `vcn` and `pcs`). From the
link it is `vcn` (verifyPeerCertByName) under another panel's name: Fastly answers SNI firefox.com with its own
certificate, valid for default.ssl.fastly.net, so the certificate must be checked against that name. Dropped, it was
checked against the SNI and failed. Now read as vcn in VLESS, Trojan, Hysteria2 and vmess's JSON, desktop and
Android, and shared back as `vcn`; a link with both keeps `vcn`. `pcs` is untouched — the owner's second link, every
TLS field, is a test on both platforms.

## The core's own key names

`serverName=` and `fingerprint=` (some generators write the core's names) are read as `sni` / `fp`; `sni` / `fp`
win when both are there. TLS and REALITY.

## What an import did not read

parser.unreadLinkKeys names the query keys a VLESS, Trojan or Hysteria2 link carries that no parser reads
(packetEncoding and remarks are harmless and not named). An import, a single link and a subscription's refresh
say them in one log line, desktop and headless service:
`Subscription "x": their links carry parameters this app does not read — foo ×12; those settings are not applied`.

## Still unsupported (named, for a later version)

Link kinds the app refuses as unsupported: `tuic://`, `anytls://`, `hysteria://` (v1), `naive+https://`, `ssh://`.

## Proven

npm test (2780): `pcn` in four link kinds, vcn winning, the share link, `pcs` byte for byte, the aliases, the unread
keys and their counts, the three callers; Android's LinkParser test in CI.
