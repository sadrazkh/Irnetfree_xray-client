# v1.7.2 — the backend you chose, IPv6 that cannot walk around the tunnel, no buffer cap on chains

A fix release, driven by three reports against v1.7.1 on the owner's own
laptop: upload speed, a DNS leak that was still there, and speed that decays
until a reconnect. What was measured, what was found, what changed.

## What was found

- **The xray config for the reported server is byte-identical from v1.2.0 to
  v1.7.1.** Every version's builder was run over the same store; the live
  `config.json` equals the v1.7.1 build. Whatever changed between versions,
  it was not the config the core runs.
- **The app was running tun2socks, not sing-box.** The setting said sing-box,
  sing-box was installed (userData/bin), and the log said "sing-box not
  installed — TUN falls back to tun2socks". sing-box loads `wintun.dll` only
  from its own directory; the bundled `wintun.dll` sits beside tun2socks in
  resources/bin, and nothing ever copied it over. Every install with a
  downloaded sing-box has been on the gVisor stack of tun2socks since v0.14.0.
- **The DNS leak, reproduced live:** the Wi-Fi adapter kept the router's
  link-local IPv6 resolver (from a Router Advertisement), because the
  tun2socks backend has no IPv6 peer and the guard only overrides a family it
  has a peer for. Windows sends a query to the other interfaces' resolvers
  whenever the preferred one is slow or answers REFUSED — a TXT lookup the
  hijack refused reached the router over `fe80::` and went on to Google from
  the ISP's IPv6 prefix. The laptop also has global IPv6 addresses and a v6
  default route through Wi-Fi, so on tun2socks every IPv6 packet left outside
  the tunnel as well.
- **The owner's DNS lists overlap:** `1.1.1.1` is both an in-country plain
  resolver and the remote DoH server. The direct rule matched on address
  alone, so the DoH connection went off the tunnel too, from the machine's
  own address.
- **`policy.levels.0.bufferSize: 0`** was set for any plan with a WireGuard
  dialled through a chain (Xray-core #2850). Level 0 is every connection of
  the config, and a pipe allowed to hold nothing makes each write wait for its
  reader: the whole corporate plan ran lock-stepped, both directions. Both
  cores (26.3.27, PattN 26.9.1) carry the chained WireGuard without it now.
- **v1.7.1's DNS refresh spawned PowerShell every 30 s** of a session — a
  second or two of CPU each time — to learn that nothing had changed.
- Upload through the tunnel swung between 50 KB/s and 550 KB/s within
  minutes on the same instance, with the raw Wi-Fi upload at 90–450 KB/s in
  the same runs. The link, not the client, sets that ceiling; the version
  difference the owner saw is not reproducible from the code or the config.

## What changed

- **sing-box is used when it is installed.** `wintun.dll` is copied beside a
  downloaded sing-box at connect time (logged: `wintun.dll copied beside
  sing-box`). System stack, `auto_route` with IPv4 and IPv6, `strict_route`
  for the strict guard, per-app routing — the backend the setting names.
- **tun2socks carries IPv6 too** (Windows): the adapter gets
  `fdfe:dcba:9876::1/126`, its v6 resolver is the tunnel peer, `::/1` and
  `8000::/1` are pinned to it, and the leak guard now overrides the IPv6
  family of every physical adapter as it does IPv4. Best effort: if the v6
  setup fails it is logged and v6 stays as it was.
- **Direct resolver rules match the port** (`53`, or the entry's own): a public
  address shared with a remote DoH server keeps its DoH on the exit.
- **No `bufferSize: 0`** for chained WireGuard. `scripts/probe-wg-chain.js`
  passes on both cores plain, over TLS, with 80 ms RTT and with the fork's
  mask; `IRNF_PROBE_BUF0=1` puts the old line back for a comparison.
- **The DNS refresh is cheap:** `netsh interface ipv4|ipv6 show dnsservers`
  (tens of milliseconds, no PowerShell) every 30 s; the PowerShell snapshot
  only on a drift, on the first tick and every tenth (five minutes), which
  is also when an adapter that came up since is journaled.
- **xhttp `extra` from share links reaches the core** (xmux, padding,
  `scMaxEachPostBytes`, the uplink method): it was parsed out and dropped.
  The core ignores unknown keys inside it and its own host/path/mode win.

## Validation

`npm test` 713/713 (Windows, macOS, Linux in CI). `npm run validate`
183/183 on the official core, 195/195 on PattN + sing-box (12/12 TUN).
`scripts/probe-dns-leak.js` 36/36 on both cores. `npm run probe:wg` 2/2
with and without the old buffer cap. On loopback (official core, client →
hop → sink, 100 MB × 4 each way) the cap cost a third of the download rate
(median 602 MB/s against 948 MB/s) and a tenth of the upload (459 against
503 MB/s); on a real link every write of a capped pipe waits for the reader
in addition. The tun2socks IPv6 lines and the wintun copy are pinned by unit
tests; neither could be run on a live tunnel here.

## What to watch

The first connect after this update runs sing-box on machines that used to
fall back to tun2socks. If the TUN adapter does not come up, the log says so
and **Settings → TUN backend → tun2socks** restores the old path; report the
log lines. The IPv6 path on tun2socks has not been exercised on a real
adapter: a failure there is logged and leaves v6 as before.
