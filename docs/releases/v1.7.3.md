# v1.7.3 — the core no longer dies on a corporate WireGuard, and the network does not get to place its endpoint

A fix release for the reports against v1.7.2: "speed and stability are wrecked,
advanced routing with the corporate WireGuard no longer brings the company
sites up". What was measured on the owner's laptop, what was found, what
changed.

## What was found

- **The core was crashing.** The advanced plan's chain ends at a corporate
  WireGuard whose endpoint is a NAME (`cobra.tes.ca:42421`). The endpoint was
  only ever resolved by the app for the patterniha fork; on the official core
  the name went into the config and the core resolved it with its own DNS. The
  plan's corporate resolver (`192.168.60.1`, reachable only through that same
  WireGuard) was the last server in that DNS and, in serial mode, was asked
  for the endpoint of the tunnel that reaches it. It could not answer, and
  Xray's WireGuard handler then panicked:

      [Error] IPC error -22: failed to set endpoint cobra.tes.ca:42421: app/dns: record not found
      panic: close of closed channel
        proxy/wireguard.(*netBind).Close   bind.go:111
        proxy/wireguard.(*Handler).processWireGuard.func1   client.go:133

  One connection to a corporate address and the whole process was gone: every
  other route with it, the kill switch (on) closing the internet behind it.
  That is the "unstable, have to reconnect", and it was reproduced on the
  laptop with the store as it is. The chain had been moved onto the official
  core when its first hop became the xhttp server, so the guard rail that only
  covered the fork silently stopped applying.
- **The corporate resolver answered for the whole internet.** The same log
  shows `api.ipify.org` and `speed.cloudflare.com` being asked of
  `192.168.60.1` whenever the public DoH pair failed — each one a full round
  trip into a tunnel that was not up.
- **Managed DNS had been switched off in the store** (it was on the day
  before). With it off the corporate resolver is not in the config at all, so
  names inside the company network cannot resolve in TUN mode, and the leak
  guard pointed every physical adapter at the tunnel peer — which answers
  nothing once the core stops hijacking port 53. Nothing in the log said
  either thing.
- **The network the laptop was on hijacks everything.** Its resolver
  (`irnetfree_help.lan`, 192.168.10.1) answers every name from 198.18.0.0/15
  with a fc00:: companion — a fake-IP gateway — and one middlebox terminates
  TLS for every SNI: the real server address, the fake one and docker.com
  itself all returned the same certificate (issuer "YR1"). REALITY refuses
  that correctly ("received real certificate, potential MITM"). No client
  works through that network; the raw link measured 2.3 MB/s down, 0.7 MB/s
  up. That is the whole of the "speed" on that Wi-Fi.
- The xhttp `extra` honoured in v1.7.2 is not in the owner's stored server
  (the record predates it); it changed nothing here.

## What changed

- **Every core gets the WireGuard endpoint as an address**, resolved by the
  app before the config is written, and through `src/main/trustedDns.js`: the
  OS resolver first, and when every answer it gives falls in a range no public
  server can be in (198.18.0.0/15, RFC1918, loopback, link-local, fc00::/7…) a
  DoH lookup over HTTPS to a literal-IP resolver with a verified certificate.
  On the hostile network above the endpoint came back as `51.222.52.23` from
  DoH while the network said `198.18.175.48`; the log says so. With that, the
  same plan, the same five connections: core alive, zero panics.
- **A target resolver with search domains is pinned to them** (`skipFallback`):
  it is never the fallback for the names the tunnel itself needs. Without
  search domains it stays a fallback, as there is nothing else to match on.
- **The leak guard follows the adapter, not the peer.** When the core hijacks
  port 53 the physical adapters still get the tunnel peer (fail-closed). When
  it does not — managed DNS off, or a sing-box-format config — they get what
  the TUN adapter got, the user's own resolvers through the tunnel.
- **A warning when managed DNS is off and the plan carries a WireGuard with
  its own resolver**, naming the resolver and the setting to turn back on. The
  same is in the README and the setting's own hint.
- **A WireGuard endpoint the app placed is excluded from the tunnel** when the
  peer is dialled directly, like a server address.

## Validation

`npm test` 726/726 (Windows, macOS, Linux in CI). `npm run validate` 183/183
on the official core, 195/195 on PattN + sing-box (12/12 TUN).
`scripts/probe-dns-leak.js` 36/36 on both cores. `npm run probe:wg` 2/2 with
the pinned corporate resolver. The owner's own advanced plan, on the hostile
network, run as a throwaway core: before the fix the core died on the first
corporate connection; after it, five connections (internet, corporate name,
corporate DNS over TCP, a corporate host, internet again) and the core is
still running, the corporate resolver asked nothing outside its domains.

## What to watch

Turn **Settings → DNS → "DNS managed by the app"** back on before testing
the corporate chain: without it the company names cannot resolve, and the app
now says so in the log at connect. Test on a network whose DNS is not fake-IP
(the log line `WireGuard endpoint: this network answered … using … from DoH`
tells you when it is). Whether the chained WireGuard carries data with the
default pipe buffer (v1.7.2 removed `bufferSize: 0`) has still not been seen
on a real corporate link, only on the loopback probe; if the tunnel handshakes
and then passes nothing, say so and it goes back.
