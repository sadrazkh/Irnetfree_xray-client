# v1.38.2 — the router's sign-in page is easy to find

By the version rule: improvements to something that already exists (the transparent mode's sign-in page), so the
third number goes up.

## What the owner reported

«الان همون http ها هم ریدایرکت نمیشن … خیلی سخته اون صفحه رو پیدا کردن», and: one sign-in opened the internet
for everyone, and the router did not tell the users apart.

## What it was, on his network

His laptop sits behind a second router, a TP-Link at 192.168.1.1 with its own subnet, whose upstream is the
IRNetFree router at 192.168.2.1. A router in router (NAT) mode hides every device behind it. The main router sees
one MAC and one address, so:
- one sign-in lets that whole router through;
- nobody behind it is told apart;
- nobody behind it is sent to the page again, because to the gateway they are signed in.

No software on the main router can tell devices behind a NAT apart. The fix is on the network: the second and
third routers go to Access Point mode, or WDS for the one on Wi-Fi. The owner chose to do that, and chose no
detection in the app for now.

The https change in v1.38.1 did not stop the http redirect. A real Chrome, driven against the portal with an
http:// address, tried https first, fell back to http and landed on the sign-in page. It did so with tcp/443
refused, answered by plain HTTP (v1.38.1), or connected and silent.

## The owner's three picks, built

- **A short name on the router's DNS.** While the page is up, `login.lan` points at it. It is a line in
  `/tmp/hosts/irnetfree-portal`, the directory OpenWrt's dnsmasq reads as `--addn-hosts`, followed by
  `killall -HUP dnsmasq`. The line is removed, with another HUP, when the page goes down. The port stays in the
  address (`http://login.lan:30822/`), because :80 belongs to LuCI. A request to the name is redirected to the
  address, so the form keeps one origin.
- **The address after a sign-in.** The status page ends with the page's addresses to bookmark, the name's first,
  since a device that is signed in is no longer sent there by itself.
- **On the Users page (router, login mode),** a "sign-in page" box shows the name's address and the numeric one,
  each with Copy, the QR of the first, and "Print for the wall". That prints a sheet in Persian and English
  whatever the window's language: join the Wi-Fi, the page usually opens by itself, otherwise scan or open the
  address, then the username and password. While the page is down the box says so.
- The users payload (`lanusers:get`) carries `portal: { url, name?, nameUrl? } | null` on the router only.

## Proven

- `npm test`: 2878 pass, 9 skipped.
- The router: the hosts line and the HUP while the page is up, both gone with it, the redirect of the name, the
  status page's two addresses, and portalInfo().
- The IPC: `portal` only where the service hands it in, and null when it throws.
- The Users page: the box, Copy, the QR of the name, the printed sheet (in the page while it prints, gone
  after), no box in block mode or on a desktop, and only http addresses drawn.
- tests/lanUsersPortalBrowser.test.js in a real Chrome, again.
- A headless render of the box (fa 1080 px, en at 390 px) and of the print sheet under print media.
- The QEMU job on 23.05 and 24.10 checks `/tmp/hosts`, `killall`, and that dnsmasq answers a name from a file there
  after a SIGHUP.

## Not proven

- On the owner's AC-1304: the name from a phone, and a sheet on real paper.
- A device with Private DNS or DoH resolves `login.lan` elsewhere. The box says so, and the numeric address works.
