# v1.18.0 — ECH, the newer link parameters, Hysteria2, a newer default core, and fastest per subscription

Asked for by the owner: the settings recent v2rayN and Xray(-PattN) links carry and this app did not read — ECH first
(`ech=cloudflare-ech.com+udp://1.1.1.1`) — handled completely, on every platform at once. First published as the
pre-release **v1.18.0-beta.1** for testing; the owner tested it ("it looks right") and asked for three more things
before the final tag — they are the next three sections.

## A newer default core (Windows, macOS, Linux, the router)

- **Xray 26.9.30 by default.** A plain download — the first install, the Update button in Required files, the weekly
  updater — installs the newer of GitHub's latest stable release and the version this release suggests (⭐ in the
  picker, coreVersions.js). XTLS has marked every release after 26.3.27 a pre-release, so "latest stable" alone kept
  every new install on March's core; v2rayN 7.25.4 (stable) ships 26.9.30. A newer stable from XTLS still wins, and an
  install is never moved below what it has. An existing install moves when Update is pressed (or by the weekly
  updater when it updates cores). Xray-PattN and sing-box install what they did (their latest stable is newer than
  their ⭐).
- **Checked in CI on every push:** a new job hands the suggested Xray, Xray-PattN and sing-box every config shape this
  app writes (plans, DNS modes, TUN, the v1.18 link forms) through `xray run -test` / `sing-box check`.
- **ECH on an old core:** the official Xray knows `echConfigList` from 25.7.26 and `echSockopt` from 25.8.3; an older
  one passed the config and connected WITHOUT ECH. Such a core now hands the server to Xray-PattN when it is
  installed, and otherwise the connect is refused with "update Xray under Settings → Required files". The router's
  opkg fallback core (24.12.31 / 25.1.30) is the case this catches.

## Fastest and ping per subscription (Windows, macOS, Linux, the router's web UI, Android)

- Every group with two or more configs — each subscription, and what was added by hand — has 📶 (test all of it: TCP
  and real delay) and ⚡ (connect to its fastest) on its header. The home picker lists "⚡ Fastest — <subscription>"
  under ⚡ Auto when there are two or more groups.
- A group's ⚡ tests the group again unless all of it was tested in the last 3 minutes, then connects to the best
  (real delay first, the TCP handshake as the fallback — Auto's ranking). The global ⚡ Auto is unchanged.
- Android runs its own ⚡ (handshakes to all, then real round trips through the quickest) on the group only.

## Mux, decided per server by a test (every platform)

Field report before the final tag: the router ran well for two to three hours, then "kept disconnecting", and a
restart did not help. Its log held hundreds of WebSocket dials to the ECH server ending in EOF / broken pipe in the same
milliseconds. Measured from the same line:

- 26.3.27, 26.9.30 and Xray-PattN 26.9.1 all carried 34 of 34 connections with ECH (4 in sequence, 30 at once), so the
  core version is not the cause.
- Plain DNS to 1.1.1.1 answers with a fresh ECH key, while DoH to 1.1.1.1 is blocked on this line.
- A handshake swings from 0.6 s to 3.7 s as the line does.

A router turns every flow of every device into its own TLS + ECH + WebSocket handshake on a slow CPU, and Xray leaves
a failed handshake's socket open until garbage collection (XTLS/Xray-core#6813). With mux, the same server answered a
new connection in about 150 ms, carried by a handful of real connections.

- **Setting 'Mux'**: Off (default — nothing changes until it is turned on) / Auto / On. The owner asked for Off by
  default: mux had never run on any of his clients. Recommended first on the router, where the gain is largest. Only VLESS (without flow), VMess and Trojan over WebSocket or
  HTTPUpgrade; gRPC, XHTTP and H2 multiplex already, and nothing else is touched.
- **Auto**: before the first connect to such a server, a throwaway core tries it with mux (two requests over one mux
  connection) and, if that fails, without. Mux is used only when it works. The verdict is kept per server (7 days
  when it works, 3 when it does not), and a muxed connection that drops is tested again on the next connect.
- **Mux object**: concurrency 8, XUDP concurrency 16, UDP 443 keeps its own way (skip).
- **Core log flood control** (desktop and router): a repeated core line is passed on at most five times in ten seconds,
  then once as "×N more" — a storm no longer turns into CPU spent on syslog.

## Android: current cores and a way to hear of updates

- Android 10 and newer will not run a program an app downloaded into its own storage, so the cores have to be inside
  the APK (v2rayNG lives with the same limit). The APK now carries Xray 26.9.30 (libv2ray v26.9.30, from v26.7.11)
  and Xray-PattN 26.10.3 (from 26.9.13); sing-box stays 1.13.14.
- Once a day the app asks GitHub for the latest release; a newer one shows a card on Home with a Download button (the
  release's APK). Settings lists the cores the app carries.
- **The first permanently signed APK.** The four signing secrets are in the repository now; the release build checks
  that the APK carries the pinned certificate (SHA-256 aabda682…3fc6) and refuses to publish otherwise. Phones that
  have an earlier, temporarily signed APK uninstall it ONCE (copy the subscription link first); from now on every
  update installs over the one before.

## Every platform (Windows, macOS, Linux, the router, Android)

- **ECH (Encrypted Client Hello)** — `ech=` is read into the core's `echConfigList`: a base64 config, or where to fetch
  it from DNS (`name+udp://1.1.1.1`, `name+https://…/dns-query`, kept exactly — the `+` is part of it). Under TUN the
  core's own lookup is bound to the physical adapter like every direct dial (it would otherwise enter the tunnel that is
  waiting for its answer); a resolver given by name is resolved before the connect; under the strict leak guard a UDP
  query to 1.1.1.1 / 8.8.8.8 / 9.9.9.9 is made over DoH on the same address and gets its firewall hole. On sing-box
  the same link becomes sing-box's own ECH.
- **Certificates** — `pcs` (the certificate's SHA-256 — the core's replacement for allowInsecure, a self-signed
  certificate too) and `vcn` (verify the certificate against this name instead of the SNI). A link that names its
  certificate is no longer pinned on first use; a pin it brings and one learnt on first use are sent together.
  sing-box has no setting for either, so a server with `pcs` / `vcn` that runs on sing-box skips the certificate check
  there, as allowInsecure did — on Xray both are checked.
- **REALITY** — `pqv`, the server's ML-DSA-65 key (post-quantum check). A malformed key is dropped (and refused in the
  edit form) instead of making the core refuse the whole config.
- **Transports** — gRPC `authority`, mKCP `mtu`; `insecure` / `allow_insecure` read like allowInsecure; VMess links
  read the second values where v2rayN writes them (gRPC host → authority, type → mode; kcp path → seed).
- **mKCP works again** — every 2026 core refuses mKCP's `header`/`seed` ("removed and migrated to finalmask"), so
  every kcp server failed to start. The app now asks the core it is about to run for its version and writes the masks
  in the form that version takes (header-* / mkcp-original / mkcp-aes128gcm, or mkcp-legacy from 26.6.1).
- **Hysteria2** — `hysteria2://` and `hy2://` import and run natively on both Xray cores (auth, SNI, pinSHA256, ECH,
  salamander obfs, port hopping written for the running core's version, up/down). One that asks for `insecure=1`
  without a pin runs on sing-box: the Xray cores have no way left to skip the check, and pinning on first use cannot
  work over QUIC. Its TCP ping shows "—" (UDP only); the real delay is measured — on sing-box where it runs there.
- **Shadowsocks plugins** — `obfs-local` (obfs=http) and `v2ray-plugin` (websocket, with or without tls) become the
  matching transport (sing-box runs them as plugins); any other plugin is refused by name instead of imported without
  it.
- **Edit form** — ECH, pcs, vcn, pqv, gRPC's authority (the Host field) and Hysteria2's fields; share links / QR carry
  everything back, and a subscription refresh keeps what you edited.
- **sing-box** — besides ECH and Hysteria2: httpupgrade, WebSocket early data (`?ed=`), the TLS fragment.

## Android

- The same parser, config forms and edit sheet. httpupgrade links now keep their path and Host (they were lost).
- A Hysteria2 with insecure and no pin runs — and is tested — on the bundled sing-box (arm64).
- Known limit: ⚡ (fastest) ranks by a TCP handshake first, so UDP-only servers (Hysteria2, WireGuard) are not picked
  by it; use Test on the server.

## Router (OpenWrt)

- A pre-release's package is versioned `1.18.0~beta.1` inside (its file keeps `1.18.0-beta.1`): opkg ranks it below
  1.18.0, so re-running install.sh for the final release upgrades a router that tested the beta — with a `-` opkg read
  the beta as the newer one and answered "Not downgrading". install.sh on its own fetches the latest final release; to
  test the beta, download its ipk and run `sh install.sh /tmp/irnetfree_1.18.0-beta.1_all.ipk`.

## Check on your own devices

- Paste the ECH link from the request and connect in TUN mode (standard leak guard) on Windows, then on the router and
  Android; the log must not show "Failed to query ECH DNS record".
- Edit a server: type an ECH value, save, copy the link — it carries `ech=`.
- A kcp server (if you have one) connects on Xray 26.3.27 and on 26.9.x.
- A Hysteria2 link with and without `insecure=1`: the first on sing-box, the second on Xray.
- Required files on Windows: Update on Xray installs 26.9.30 (the log line names it); the ⭐ card in Choose version is
  26.9.30.
- Servers: ⚡ on a subscription's header connects to that subscription's fastest; 📶 tests only that subscription.
  The home picker's "⚡ Fastest — <subscription>" does the same.
- Android: Settings names Xray 26.9.30 and Xray-PattN 26.10.3; ⚡ on a group's header stays inside the group.
