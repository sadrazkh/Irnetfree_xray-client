# v1.13.4 — OpenWrt: LAN clients get TCP and names

OpenWrt only; `src/main/` unchanged. On the owner's Google Wifi v1.13.3 kept
the router reachable (v1.13.3's fix held), the router's own checks worked,
but the devices behind it had no internet. The log said exactly why, twice.

## 1. No TCP for LAN clients — the firewall zone's `input`

Every LAN flow that reached the core in the log was UDP (QUIC, NTP, DNS);
not one TCP flow. sing-box's `system` stack hands every TCP connection from
the tun to the kernel as **INPUT on the tun device** (a local listener on the
tun's own address does the L4 work), while UDP never leaves userspace. The
`irnetfree` firewall zone that v1.13.0 created had `input REJECT`. UDP
passed, TCP died at the zone.

The uci-defaults script now creates the zone with `input ACCEPT`, and on an
upgrade — it runs again — repairs an existing zone's `input`. The QEMU smoke
asserts the option and, more to the point, now fetches a page **through the
tunnel** (see 3).

## 2. No names — plain DNS rode the proxy as UDP

`udp:1.1.1.1:53 [socks-in -> proxy]`, never answered: the router's settings
had "DNS managed by the app" off (a stored value, from the desktop's backup
or by hand), and with it off dnsBuilder emits no port-53 hijack — so every
plain DNS query from dnsmasq and from the clients went to the proxy server
as UDP, which most servers do not carry. On a router that switch has no
meaning: the managed plan is what makes the core answer every port-53
packet. The service now forces `dnsManaged: true` on OpenWrt (after the
stored settings; `settings:set` answers with the forced value) and the UI
hides the switch on the router.

## 3. The core's SOCKS inbound came up after the tunnel

`dial tcp 127.0.0.1:30808: connect: connection refused` for the first seven
seconds of every connect: the core takes ~9 s to bind its inbound on the
AC-1304, `start()` returns after 1.2 s, and the tunnel was already forwarding.
On OpenWrt the service now waits (up to 20 s) for the SOCKS port to accept a
connection before starting the gateway.

## The smoke got real

The QEMU guest now runs a second sing-box as a plain SOCKS server on the LAN
address (bound to `br-lan`, so it can never loop into the tunnel), registers
it as the server, connects, and then — from the router, whose unbound sockets
go to the tunnel — fetches `http://1.1.1.1/` (TCP through tun → sing-box →
socks → xray → upstream → internet; this dies with `input REJECT`) and
resolves `example.com` against `1.1.1.1` (a plain UDP query, answered by the
core's hijack). Both on 24.10.2 and 23.05.5.
