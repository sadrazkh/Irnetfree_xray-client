# v1.9.0 — the Android app gets the second core and the design; the share QR is scannable again on both

Three things, in the order they matter to somebody holding a phone.

## The share QR was not scannable — on Windows either

A share link carries every setting, so it is long: an xhttp config with an
`extra` object, or a WireGuard peer, runs past 600 characters, and the code
that encodes it is 85 modules square. Both clients drew it badly.

**Desktop.** `showServerQr` asked the library for a fixed-size GIF
(`createImgTag(4, 6)`) and `styles.css` had no rule for `.qr-image` at all.
Measured in the renderer: a 621-character link produced a 352px image inside a
243px box — 109px of it hanging outside the modal — and the 6px margin was 1.5
modules where the QR specification requires 4, so the part that was on screen
was one a scanner is entitled to refuse. It is now a scalable SVG with a
16px = 4-module quiet zone, and the stylesheet gives it a bounded white plate.
Every link length the app can produce fits, down to 2.5px per module for a
1200-character link.

**Android.** ZXing was asked for a 640px bitmap, which makes a module a
non-integer number of pixels — it rounds, so some modules came out a pixel
wider than their neighbours — at a cost of 409,600 `setPixel` calls on the
composition thread, and Compose then resampled the result with its default
bilinear filter. Three separate ways to soften the edges a scanner has to
threshold, on top of a 1-module quiet zone. It now encodes at the matrix's own
size, one pixel per module, and the `Image` scales it with
`FilterQuality.None`, so each module is a crisp square at any size.

`tests/qrShare.test.js` pins both halves and the property behind them: for
every link length, the code fits the modal with at least 2px per module.

## Xray-PattN runs on the phone

A config with no TLS — plaintext VLESS or Trojan to a public address — is
refused at load by the official core, and plenty of Iranian configs are
exactly that. On Windows the answer since v1.2.0 has been to run that config
on the patterniha fork; on the phone there was no such choice, so those
configs simply failed with an error that reads like a bug in this app.

The fork publishes an Android binary, so it is bundled the way sing-box
already is: `fetch-libs.sh` puts it in jniLibs as `libxraypattn.so` — the only
place Android will execute a file from — and `XrayPattnCore` runs it as a
subprocess with a SOCKS inbound, which the TUN already reaches through
hev-socks5-tunnel. Unlike sing-box it needs no translator: it takes the very
same JSON `ConfigBuilder` already produces, so it works for every plan shape,
chains and pools included.

`EngineChoice.kt` is the desktop's `engineChoice.js`, function for function,
and its test is that file's assertions transcribed: a single server takes its
own choice; a chain, pool or advanced plan runs on PattN as soon as **any**
server in it asks for PattN; sing-box stays single-config only. That last rule
is why this had to be a port and not a flag — the phone previously looked at
`plan.server.engine` and nothing else, so a chain with a PattN hop ran on the
core that refuses it.

Latency tests follow the same rule, so a config that needs PattN is no longer
reported dead by a test run on a core that will not load it.

Settings gains an app-wide **Default core**; the per-config picker gains
Xray-PattN. When the binary is not bundled for the device's architecture
(arm64 only) the plan falls back to the in-process core and the log says so.

**The APK grows by about 19 MB** for the extra core.

## The design

The app still looked like the first sketch — blue on navy, five tabs, a Home
screen that was a column of Material cards. It now follows the design doc:
mint (`#35e0ac`) on a near-black green, metrics in mono, and four tabs —
Connect / Servers / Subs / More, with Proxy Pool moved in beside the other
advanced screens.

- **Connect** is built around the ring: a mint disc with a ring pulsing out of
  it when the tunnel is up, a dark disc with a hairline when it is not; then
  the state and its reason, the selected exit, four metrics, a transfer-speed
  sparkline, and the tunnel's real scope.
- **The protection strip** says only what a phone can actually see. The
  desktop's kill switch and leak guard are Windows adapter work; Android's
  equivalent is the system's own "Block connections without VPN", which is not
  ours to report. The chips are the resolver mode, the routing mode, whether
  the geo files are really on the device, IPv6, and the core a plan would
  really run on.
- **Simple / Advanced** is real, not decoration: simple mode leaves Connect as
  one ring and one decision and More as four rows. Nothing is deleted, and it
  defaults to advanced so an upgrade never hides work already set up.
- **Servers are grouped** by where they came from — yours first, then a
  section per subscription.
- **Subscriptions auto-update.** The setting has been in the model since the
  beginning and was read by nothing; they now refresh when the screen opens.

Space Grotesk and JetBrains Mono are not bundled: a font that fails to
download breaks the build, and the platform monospace carries the design's
character. Swapping the real families in later is a `res/font` drop and one
val.

## What this release cannot claim

No Android device was in the loop. The config, the DNS plan and the engine
choice are verified against the desktop's own test assertions, and the app
compiles and passes 47 JVM tests in CI — but the PattN subprocess actually
carrying traffic, the new Connect screen on a real screen, and the QR being
read by a real camera all need the APK on a phone.

The desktop is otherwise untouched: `npm test` 794/794, and nothing under
`src/main/` — the whole connect path — differs from v1.8.0.
