# v1.42.0 — Direct ports: local ports that leave outside the VPN

By the version rule: a new capability, so the second number goes up.

## What the owner asked

He wanted a tool such as the Plus scanner to work while the VPN is on: "leave a port open for outside the VPN, and it
uses that, optionally", and in the main client "open a SOCKS port direct, several of them".

The reason is a real one, measured on his laptop on 2026-11-02: with the VPN on, a TLS request to the reserved address
192.0.2.1 with a CloudFront name in its SNI answered 200 from CloudFront. The VPN's sniffing redials the name, so every
address "answers" and a scan measures nothing.

## What is new

- **Settings → Direct ports** (src/main/directPorts.js): a list of local ports, each SOCKS or HTTP.
- **Where it leaves:** what enters one goes straight to the machine's own internet, whatever the main connection,
  routing mode or plan is doing. The main connection may be dead.
- **Under TUN:** the exit is bound to the physical interface like every direct dial of the app. Without TUN, the OS's
  route is already outside.
- **No sniffing on them:** the core dials the address it was given.
- **Every plan:** single, chain, advanced, pool, a raw JSON config, and a config sing-box runs whole (TUIC, AnyTLS). Bound
  to the interface there too, where the sing-box builder's own `direct` is not.
- **The list empty (the default):** every config is byte-identical to before.
- **Loopback only, and no password.** A port for other devices already exists: a LAN user with a direct route.
- **While connected only:** the core holds the ports. A changed list asks for a reconnect like the other ports.
- **Names:** `AsIs`, so a name is the OS's to resolve; `direct`'s `UseIPv4` asks the core's DNS, whose queries ride the
  exit.
- **A port something else holds** is not opened, and the log says which. The page refuses it first where it can see it
  (the app's own ports, the pool); the users' proxy page refuses a direct port too.

## Not in this round

- **Android:** no direct ports. The phone has no use for one yet, and its config builder is separate.
- **The router's page** hides the list: a loopback port serves nobody on a router, whose LAN has the users' page. A
  config that carries the key still builds it.

## Tested

- `npm test`: tests/directPorts.test.js.
- **The cores gate** (scripts/validate-configs.js): `direct-ports-*` on the suggested Xray and Xray-PattN; `sing-box
  check` of the TUIC and AnyTLS configs with them.
- **scripts/probe-direct-ports.js** in CI, both Xray cores and sing-box, the app's own config with a dead server:
  - a page answers through the direct SOCKS and HTTP ports;
  - the bytes are on `dp-direct` in /debug/vars;
  - another name in Host does not replace the address, while on the app's own port (sniffing on) it does, which is the
    control;
  - an empty list writes the config of before.
- **scripts/tun-dns-probe.js**, the real sing-box TUN in a namespace: a site past the default route sees the physical
  address through a direct port. The control leaves the bind out, and the dial must enter the tunnel and never arrive.

- **The owner's laptop, Windows, his VPN on in TUN mode:** a throwaway core of this builder beside the running app, its
  own ports, killed after. Cloudflare's trace said `loc=NO` plainly (the VPN), `loc=NO` through a direct port with no
  bind (it re-enters the tunnel), and `loc=IR` through a direct port bound to Wi-Fi.

## Owed

The owner's own app with a direct port in Settings, then Plus scanning through it. The laptop check above ran a
throwaway core and named the interface by hand; the app picks it at connect (`tun.physicalInterface`).
