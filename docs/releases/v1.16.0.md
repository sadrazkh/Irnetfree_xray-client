# v1.16.0 — The router: a status you can trust, a kill switch, LuCI pages and remote control

A router release, asked for by the owner after v1.15.0: "it suddenly shows disconnected", a kill switch, an option to
come up connected, settings inside LuCI like PassWall, and control of the home router from outside — with no static
IP, behind any NAT, and not through the VPN. Desktop and Android are unchanged (the desktop only gets the page-load
state fix, for parity).

## Router (OpenWrt)

- **No more phantom "Disconnected".** The page never asked the service for the connection's state on load, so every
  reload — a phone bringing a background tab back, F5 — showed «قطع شده» and uptime 00:00 while the tunnel was up,
  and pressing Connect there tore the gateway down for 20-40 s. The page now reads the real state on every load and
  after every reconnect of its event stream, and Connect on the connection that is already up does nothing.
- **Network blips no longer drop the VPN.** The network watcher rebuilt the whole connection on any address change —
  an ISP rotating the IPv6 prefix, a WAN or PPPoE flap. On the router it now looks only at the WAN (the interfaces
  holding the default routes, from netifd), waits 10 s, and asks the tunnel itself (an HTTP 204 through the local
  SOCKS, twice): the connection is rebuilt only if the tunnel really stopped answering, or the WAN device the core
  dials through is gone. The log says what changed and what was decided.
- **States that say what is happening.** A drop shows "Reconnecting… (attempt n)" through its whole backoff, boot
  retries show "Waiting for internet… (attempt n)" — never a bare "Disconnected" or a flickering "Error".
- **A service that never stays dead.** An uncaught error ends in an orderly shutdown that procd always restarts
  (respawn never gives up), `app:quit` restarts it instead of leaving it half-alive, the token is compared in
  constant time, and every line the service prints is found by `logread -e irnetfree`.
- **Diagnostics.** Every state change is logged once with its cause (user, boot, recovery, switch, netwatch) and
  the memory at that moment (MemAvailable, the RSS of node, xray and sing-box); a 500-line log and a
  "Copy diagnostics" bundle (no secrets) for LuCI; no test core is started right after a connect any more.
- **Kill switch.** While the VPN is on but the tunnel is not carrying traffic — a rebuild, a crash, boot before the
  first connect — devices on the LAN have no internet. Never blocked: devices excluded from the VPN, the LAN itself
  and the modem's page (private addresses), replies of port-forwarded connections, and the router's own traffic.
  Turning the VPN off gives everyone normal internet. It lives in its own nftables table that rebuilds and crashes
  never touch, and a boot script (`irnetfree-ks`, before the network comes up) puts it back after a reboot;
  `/etc/init.d/irnetfree-ks stop` lifts it by hand.
- **Connect when the router starts** says what it does: after a reboot or a power cut the VPN comes back exactly as
  it was, with the same config; if you had turned it off, it stays off.
- **LuCI app — Services → IRNetFree.** Overview (live state, the VPN switch, a config picker grouped like the app —
  each subscription, manual servers, chains, pools, advanced routing — Connect, Reconnect, Test connection, Update
  subscriptions, Open the full web UI), Settings (connect when the router starts, kill switch, block QUIC, devices
  that bypass the VPN from the DHCP list, the web UI's port and listen address), Remote access, and Log with Copy
  diagnostics. Changes apply at once; LuCI and the web UI read the same store, so they never disagree. English, and
  Persian when LuCI is in Persian (the tab names too, through a translation catalog built with the package). Under
  the hood: an rpcd plugin calling the service's loopback-only API.
- **Remote control from anywhere.** The router keeps an outbound WebSocket to a relay you host; you open the relay
  from any network, sign in, and get your home router's full IRNetFree UI — turn the VPN on or off, switch
  configs, everything. No static IP, no port forward, any NAT. The router's side of that link never rides the
  tunnel (its addresses get their own routing rule and an xray direct rule), so you can fix a broken VPN remotely;
  if the direct path is blocked it falls back to dialing through the tunnel. The UI token never leaves the router.
- **Cloudflare Tunnel** as a second remote path: install `cloudflared` from LuCI, paste the tunnel token, and its
  edge connections are kept out of the tunnel too (http2 only — QUIC is dead on Iranian ISPs; it cannot fall back
  through the VPN).

## The relay (`relay/`)

A zero-dependency Node container for Harbora or any Docker host: the owner's password from the `RELAY_PASSWORD`
secret (12+ characters), signed 30-day sessions that a password change ends, failed logins limited per client and
overall, a device token per router (shown once, stored hashed), the router's pages streamed through (live status
included), static files cached per router and version. `docs/remote.md` covers deploying it, pairing a router, the
Cloudflare walk-through and the security notes. A relay outside Iran stops working when international links are cut;
the same image on a server inside Iran keeps working.

## Check on your own devices
- Router: leave the UI open on the phone, background the browser for a while, come back — Connected with the right
  uptime; press Connect — nothing rebuilds.
- Kill switch on, `killall -9 sing-box` over SSH: a LAN laptop has no internet until the tunnel is rebuilt, an
  excluded device keeps it; turn the VPN off in LuCI — everyone has internet.
- Reboot with the VPN and the kill switch on: no LAN internet until the tunnel is up, then it comes back by itself.
- LuCI: switch config, toggle the VPN, change settings — the web UI shows the same.
- Remote: deploy the relay, pair the router, open the relay on mobile data, switch config and toggle the VPN.
