# v1.9.3 — Android: the subscription host is resolved over DoH, and a failure now says who answered for it

Android only. Nothing in `src/` changed (`npm test` 796/796).

## What v1.9.1 did not fix

v1.9.1 routed the subscription fetch through the tunnel when there is one, and
put `TrustedDns` in front of the direct path. The direct path still failed with:

> TLS handshake failed — something answered for the panel and it was not the
> panel. Over your normal network…

The message was right and the fix was in the wrong place. `TrustedDns` believes
the operating system's answer **unless every address it returns is in a range
no public server can be in** — 198.18.0.0/15, RFC 1918, and so on. That test
catches a fake-IP gateway. It does not catch what a subscription host actually
gets on a filtered network: a **public** address belonging to the censor.
Perfectly routable, not suspect by any test of the number itself — and the TLS
handshake then fails, because the machine it reaches was never the panel.

## What changed

- **A subscription host is asked of DoH first**, not the OS. That is the
  opposite of `TrustedDns`'s own order, and deliberately: a subscription URL is
  exactly the name worth one extra round trip, and the DoH server's own
  certificate is verified by the platform, so the middlebox cannot answer for it
  either. The OS is the fallback, and if both come up empty the platform lookup
  still runs — this can only add answers, never remove ones that worked.
- **A TLS failure now says who answered.** `CertPin.describeLeaf` dials the host
  again with verification off and reports the address reached, the name on the
  certificate and its issuer, e.g.

  > [sub.example.com -> 10.20.30.40 (doh); 10.20.30.40 presented "sub.example.com" issued by "YR1"]

  "Handshake failed" cannot tell a censored panel from a broken one. The name on
  the certificate can, and the JSSE exception never carries it.
- **The full error reaches the log.** It was being written into a Toast, which
  truncates — so the parenthesised detail, the one part that identifies the
  cause, was cut off exactly when it mattered. Failures now go to More → Logs in
  full, and the toast just points there.

## If it still fails

The log line now carries everything needed to tell the three cases apart:

- issuer is something like `YR1`, or the name on the certificate is not your
  panel → the network is intercepting; the tunnel is the way round it.
- the address after `->` is not your panel's → DNS is still being answered by
  somebody else, and DoH did not get through either.
- the certificate is right and the handshake still fails → the panel's own TLS,
  or a certificate authority this Android version does not carry.
