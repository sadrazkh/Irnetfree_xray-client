# v1.9.6 — Android: TLS 1.3 on every Android version, which is what the subscription needed all along

Android only. Nothing in `src/` changed (`npm test` 796/796).

## The cause, measured

Five releases (v1.9.1–v1.9.5) chased the owner's subscription failure with
theories about the network: a tunnel that the app's own requests do not ride,
poisoned DNS, a middlebox certificate, a ClientHello killed for its SNI. Each
was plausible, each was built from the words "Handshake failed" and nothing
else, and none could have helped. What settled it was finally fetching the real
URL from the laptop and asking the server what it accepts:

```
TLS 1.3 only            -> HTTP 200  TLSv1.3  TLS_AES_256_GCM_SHA384
TLS 1.2 only (max 1.2)  -> alert protocol version (70)
openssl s_client -tls1_2 -> alert protocol version (70)
```

**The panel's Cloudflare zone has Minimum TLS Version = 1.3.** A TLS 1.2 client
is refused before any certificate is sent — which is exactly the "no certificate
arrived" the v1.9.3 probe kept reporting, and which I read as interference.

Android's platform TLS (the Conscrypt inside the OS) only gained TLS 1.3 in
**Android 10**. On Android 8 and 9 it stops at 1.2, so every request this app
made to that zone — OkHttp, the raw probe, DoH to 1.1.1.1 — got `protocol
version` back and surfaced as `SSLHandshakeException: Handshake failed`,
tunnel on or off, on any path. Everything that worked carries its own TLS
stack: Chrome (BoringSSL), the Windows client (Node), Go-based apps — and this
app's own Go core, which is why the VPN worked on that same phone while the
Kotlin fetch beside it did not.

## The fix

**Conscrypt is bundled** (`org.conscrypt:conscrypt-android`, the same code the
OS ships, a few years newer) and installed as the first security provider in
`IRApp.onCreate`, before anything opens a socket. It serves OkHttp,
`HttpURLConnection`, the certificate probe and DoH alike, so the app speaks
TLS 1.3 on every Android version it runs on. On Android 10+ nothing observable
changes.

Every TLS failure report now prints the **whole cause chain** — the alert
number, the OpenSSL error string — and **what this device can speak**
(`this device: TLS 1/1.1/1.2/1.3 via Conscrypt, Android API 28`). Had either
line been in the first report, this would have been one release.

Server-side, the same problem has a one-click fix the owner may want anyway:
Cloudflare → SSL/TLS → Minimum TLS Version → 1.2. That would also unbreak any
other client on an older phone.

## What stays from v1.9.1–v1.9.5

The path work — through the tunnel when it is up, a throwaway core when it is
not, DoH-first resolution, the certificate probe, the ClientHello split as a
retry — is retained: each is cheap, each is correct for the situation it was
named after, and the failure reports they added are how a future bug gets
diagnosed in one round instead of five. Their comments now say plainly that
they were not this bug.

## What this release cannot claim

No device was in the loop. `TlsFailureReportTest` pins that a report carries
the cause chain and the device's protocols; the Conscrypt provider itself can
only be exercised on a phone. The APK grows by the size of the Conscrypt
natives (a few MB).
