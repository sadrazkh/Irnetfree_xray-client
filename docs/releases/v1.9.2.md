# v1.9.2 — v1.9.1's APK was the debug build; this is the release build

Android only. Nothing in `src/` changed since v1.9.0 (`npm test` 796/796), and
the app code is identical to v1.9.1 — this release exists because the APK
attached to v1.9.1 was the wrong variant.

## What happened

The v1.9.1 Android job reported success and attached
`IRNetFree-1.9.1.apk` — 114.4 MB against v1.9.0's 102.7 MB, for a change that
touched three source files. That difference was the giveaway: it was the
**debug** APK.

`collectReleaseDependencies` had died with `java.lang.OutOfMemoryError: Java
heap space` (`android/gradle.properties` gave Gradle 2 GB), so
`assembleRelease` produced nothing. The workflow runs
`assembleDebug assembleRelease … || true` on purpose — a tag with no APK at all
is worse than one with a debug APK — and the Collect step then found no release
output and fell back to the debug build it had made first. It said so in one
line of a 3000-line log and nowhere else, and the job was green.

So v1.9.1's APK is installable and behaves correctly, but it is debuggable and
unoptimised. Anybody who installed it should take this one instead.

## What changed

- **Gradle gets 4 GB** (`-Xmx4096m -XX:MaxMetaspaceSize=1024m`). The runner has
  it to give; 2 GB was simply too little for this project now that it links
  three cores.
- **The fallback cannot be silent again.** When the Collect step has to use the
  debug APK it raises a workflow error annotation and writes a line into the run
  summary, where it is read without opening the log. The fallback itself stays —
  it is the right behaviour, it just has to be visible.
- `tests/releaseWorkflow.test.js` pins both: the step must keep preferring
  release, keep debug as a fallback, and shout when it uses it; and the heap must
  stay above the value that ran out.

No app behaviour changed. If v1.9.1 works for you, this one works the same, only
built the way a release should be.
