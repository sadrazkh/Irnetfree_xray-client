# v1.9.1 — Android: a subscription that failed with a handshake error now loads

Android only. Nothing in `src/` changed, so Windows, macOS and Linux are
v1.9.0 with a new version number (`npm test` 794/794).

## What was wrong

A subscription that loaded fine on Windows failed on the phone with a TLS
handshake error — and "it works on Windows" was true, which is exactly why it
was misleading. The two clients were not doing the same thing.

**The tunnel.** The Android app excludes its own package from the VPN
(`XrayVpnService.applyPerApp` → `addDisallowedApplication(packageName)`). That
is necessary — the core's own outbound sockets have to leave the device rather
than loop back into the tunnel it is building — but the exclusion applies to
*every* socket the app opens, the subscription fetch included. So on the phone
that fetch always went out over the raw ISP network, while on the desktop,
whose whole system sits inside the TUN, the very same URL was fetched through
the tunnel. A middlebox that answers a censored panel's handshake therefore
broke the phone and not the laptop.

`Diagnostics.kt` has carried a comment about this since the beginning — it is
why the IP check already dials through the local SOCKS inbound. The
subscription fetch never got the same treatment.

**The resolver.** Off the tunnel, the panel's name is resolved by the phone.
On a fake-IP network every name answers from 198.18.0.0/15, so the handshake
went to a machine that was never the panel — which also presents as a
handshake failure.

## What changed

- **Through the tunnel when there is one.** When the core is running, the
  fetch dials `127.0.0.1:<socksPort>` — the core's own inbound, reachable
  because loopback is not affected by the VPN exclusion. OkHttp leaves the
  hostname unresolved on a SOCKS route on purpose, so the core resolves it at
  the far end, through the tunnel's own DNS plan.
- **Then directly, if that fails.** Neither path is always right: a censored
  panel is only reachable through the tunnel, and a panel that only serves
  domestic addresses is only reachable off it. Trying the tunnel first and
  falling back means this release cannot take away a subscription that worked
  before.
- **A trusted resolver on the direct path.** `TrustedDns` is asked instead of
  the platform: the OS first, then a DoH server over HTTPS when every OS answer
  lands in a range no public server can be in. It only ever adds answers — if
  it finds nothing usable it falls back to the platform lookup.
- **An error that says what to do.** "Handshake failed" on its own reads like
  a broken panel when it is the network in front of it. Failures now name the
  path they were on ("Through the tunnel…" / "Over your normal network…"), and
  when both attempts fail, both are reported.

`SubscriptionsTest` pins the order and the messages: one attempt when there is
no tunnel, the tunnel first when there is one, the fallback to direct, and both
failures reported with the core's own words kept intact. 52 JVM tests in CI.

## What this release cannot claim

The network itself is not testable off a device — the order and the messages
are. Whether the owner's panel now loads is a question for the phone.
