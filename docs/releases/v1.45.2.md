# v1.45.2 — A VPN client behind the router keeps working

By the version rule: a fix to something that already exists, so the third number goes up.

## What the owner reported

With the router's VPN on, his company's site would not open under advanced routing on the laptop, whichever server he set for it, while a simple config opened it. WireGuard on the laptop stopped working too. It looked as if advanced routing broke everything.

> **Correction, in v1.45.3.** The test below cannot tell who replaced the address. Measured afterwards through each server: his servers’ own inbounds replace it too, so a router whose exit does that still broke these configs. v1.45.3 fixes that from the client: a hello cut into TLS records cannot be read.

## What was wrong, measured from his laptop

With the router's VPN on, this laptop's plain traffic left through Norway, and:

- A TLS connection to `1.1.1.1` naming `www.google.com` was answered by Google's certificate. **The router replaced the address with the name.**
- A config on the laptop is an address plus, very often, someone else's name in its TLS: Reality's camouflage, a CDN front, a pinned certificate. The router sent all of those to the wrong place.

Each of his servers on its own, behind the router, in simple mode:

| Kind | Result |
|---|---|
| `xhttp` + Reality | dead |
| `xhttp` + TLS with a pinned certificate | dead (`peer cert is unrecognized`) |
| `ws` + TLS through a CDN | most work, and the company site answers 200 |

His advanced profile had a pinned server as its default and a Reality server as its rule's target. So advanced routing was not the cause. It only happened to use the two kinds the router kills. The name resolution of an advanced plan also leaves through the default, so with the default dead every name failed, which is why changing a rule's target changed nothing.

Measured on real cores, loopback: sing-box's sniff action keeps the address, Xray with `routeOnly: false` replaces it, and Xray with `routeOnly: true` keeps it.

## What changed

**On a router, sniffing reads the name and keeps the address** (`routeOnly: true`). Domain rules, the ad list and the country rules still see the name. The device's connection goes to the address it asked for. The switch still turns sniffing off. This is given when the router builds its config and is never a setting, so a router's backup restored on a desktop does not carry it.

A desktop is unchanged, since there the name still rescues a poisoned or stale answer.

## Limits

- **The router must be updated.** Until then, turning Sniffing off on the router's page has the same effect on these configs, but its domain rules then stop working.
- **A wrong address on the router.** A corporate name at a stale public address is no longer rescued on a router: the rule still catches it, and the address stays wrong.
- **A dead default in advanced routing.** Names still leave through the default, so a dead default still stops every name. Nothing says so on screen yet.
- **WireGuard behind the router.** Its UDP path was not measured, so that symptom is not claimed fixed. Through a base it depended on that base, which is one of the dead kinds above.

## Tested

- `npm test`, with tests/routerSniffing.test.js driving the router's service.
- `scripts/probe-domain-routing.js`, in CI on both suggested cores, gains two gates. Only a rule by the name reaches the next hop there, so an answer proves the name was read: with the router's setting the hop is asked for the address, and with a desktop's for the name.

## Owed

Nothing here ran on the router. After updating it, with Sniffing on and the router's VPN on: connect the laptop on the advanced profile, and open the company site and a site from a domain rule.
