# v1.34.3 — the router's sign-in page takes what a phone types

By the version rule: a fix to something that already exists (the transparent mode's sign-in page) — the third
number.

## What the owner reported

«رمز و یوزر نیم رو تو صفحه ای که میاد از رو مودم میزنم ولی میگه اشتباهه و وارد نمیشه» — on the router's sign-in
page, the username and password he set are refused as wrong.

## What a phone types that the page compared byte for byte

plan.judgeSignIn matched the username and the password exactly as typed. On a phone:

- a keyboard (or the system's captive-portal browser) capitalises the first letter — `Sadra` was not `sadra`,
  though model.js already treats «Ali» and «ali» as one user;
- a Persian keyboard's number row types ۰–۹ (some keyboards Arabic-Indic ٠–٩) — in a password box, unseen;
- a Persian keyboard may slip in a zero-width non-joiner or a direction mark.

Now both sides go through one fold (`plan.typed`: NFKC, those digits as 0–9, the invisible marks removed) — a
password typed exactly as stored still matches, a password's own letter case still counts — and a username is
matched with its case aside. The page's two boxes also ask the keyboard not to capitalise or correct (and run left
to right in the Persian page).

## Saying which it was

The page still says "wrong username or password" for both (it tells a stranger nothing), but the router's own log
now says which: `no user "x" on this router — users are made on the router's own Users page; the desktop app's are
not here`, or `the password does not match "x"'s`. Never the password.

## Proven

npm test (2765): the portal signs in `Ali` as ali, the log's two reasons, the page's input attributes; judgeSignIn
with Persian and Arabic-Indic digits, a ZWNJ, fullwidth letters, a stored Persian-digit password, a password's case.
