# v1.9.5 — Android: the subscription fetch splits its ClientHello, and the log says which path it took

Android only. Nothing in `src/` changed (`npm test` 796/796).

## What the last log showed

v1.9.4 routed the fetch through a core when one is available. The owner's log
after installing it:

```
sub.irnetfree.info -> 188.114.96.3, 188.114.97.3, 2606:4700:3035::…, … (os);
could not read the certificate (Handshake failed)
Over your normal network — connect first…
```

Two things in that, both useful:

- **IPv4 now comes first**, which is the v1.9.4 sort — so v1.9.4 was installed
  and the fetch still took the *direct* path. The throwaway core never ran:
  either there was no config to borrow (every server had come from this same
  subscription, which cannot load) or the core did not start.
- **DoH returned nothing** (`(os)`), so `1.1.1.1` is unreachable too. The
  addresses are still Cloudflare's own and the trust-all probe still gets no
  certificate at all.

So the direct path has to survive on its own, because there are installs where
there is simply no core to borrow.

## What changed

- **The ClientHello is split.** On a direct fetch, an SSL failure is retried
  with the TLS handshake's first packet written as a series of small TCP
  segments (`FragmentedSocketFactory`). This is the same technique the app
  already offers inside a config as `fragment`, applied to its own requests: the
  panel's name travels in the clear in that first packet, and a middlebox that
  matches on it cannot when no single segment contains the whole name. Only the
  first write is split, so nothing else pays for it.
- **Every failure names the path it was on** — `via the tunnel`, `via a
  temporary core (<server>)`, `via your normal network (no config to borrow)`,
  or `via your normal network (the <server> core would not start)`. The previous
  log could not distinguish the last two, which is why this took an extra round.
- `FragmentedSocketFactoryTest` checks the split against a stream that records
  every call, not through a socket — the receiving TCP stack is free to coalesce
  the pieces again, so what arrives says nothing about whether they were sent
  apart. 59 JVM tests in CI.

## If it still fails

The log now answers the remaining question by itself. `via your normal network
(no config to borrow)` means the app had no server to route around the block
with — import one config by hand (a link or QR from any working client) and the
subscription will fetch through it.
