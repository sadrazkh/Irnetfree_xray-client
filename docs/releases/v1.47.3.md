# v1.47.3 — Android: the APK installs over the one on the phone again

By the version rule: a fix to what already exists, so the third number goes up. Android only: the desktop and the
router are the same code as v1.47.2.

## What the owner reported

A screenshot of the installer on 2026-11-10: "App not installed as package appears to be invalid", with
«چرا اینشکلی میشه ؟».

## What it was

Every APK carries a number Android compares, the versionCode, and Android refuses an APK whose number is lower than
the installed one. The release workflow used its own run number for it. The repository was recreated on 2026-11-08
and that number began again at 1.

| Built in | Version | versionCode |
|---|---|---|
| the repository before 2026-11-08 | v1.47.0 | 155 |
| the repository since | v1.47.0, built again | 1 |
| the repository since | v1.44.0 to v1.46.0, built again | 2 to 10 |
| the repository since | v1.47.1 | 11 |
| the repository since | v1.47.2 | 12 |

So a phone that held any build from before the move refused every APK built after it, the two new releases included,
whether it was downloaded by hand or through the app's update card (KI-048). The signing key was never the problem:
it is the same one, and the release workflow checks it on every build.

The numbers are read from the release workflow's runs in both repositories. That the installer answers a lower
versionCode with exactly this sentence is read in Android's source: a downgrade is reported as an "invalid" package,
while a different signing key is reported as one that "conflicts with an existing package". Which build the phone
held was not asked: any build from before the move gives this result.

## What changed

- **The versionCode is made of the version itself**: 1.47.3 is 1047003, 1.48.0 will be 1048000. No counter of the CI
  is part of it, so a moved repository, a workflow that is created again or an old tag that is built again cannot
  lower it (D-031).
- **Both workflows read the number out of the APK they built.** The test workflow does on every push, against the
  version in `package.json`; the release workflow does before anything is uploaded, and a tag's APK must be the tag's
  version. An APK with a counter in it now fails the build instead of reaching a phone.

## Limits

- The twelve APKs in the table stay on the releases page as they are, with their low numbers. They install on a phone
  without the app. Use v1.47.3 or later to update.
- A pre-release and the release of the same version carry the same number, as does a tag that is built again.

## Tested

- `tests/releaseWorkflow.test.js`: the checker is run for real over a stand-in for aapt2. A code of 12 for version
  1.47.2, which is what shipped, fails it; the code made of the version passes; another version, an unreadable name
  and a missing aapt2 fail.
- CI builds both variants and reads the release APK's versionCode (`compile android`).
- **No install was tried on a phone.**

## Owed

Install v1.47.3 over the app that is on the phone now. If the installer still refuses it, the first line of
More → Logs → Share (it names the installed version) and the exact sentence of the installer are what the next step
needs.
